# 操作を反映する

cockpit skill の SKILL.md から分けた細部。`【操縦席】未反映の操作があります` が届いたとき、hook が未反映の操作の件数を出したとき、深田に話しかけられたターンの最初に cockpit.user.json に未反映の操作があるときに読む。

`cockpit.user.json` は `{ "ops": [...] }`。各操作は `op_id`（連番）・`at`・`item_id`（カードの id）・`item_rev`・`type`・`option_id`・`undo_of`・`target`・`text`・`terminal`（`talk` で窓が相談のタブを立てたときの端末の handle）・`answer` と `choice`（`ask_decide` だけ。下の 4）・`via`・`to`・`key`（type の `answer` だけ）。`type` は `decide`・`accept`・`sent`・`skip`・`delegate`・`talk`・`ack`・`revert`・`undo`・`repeat`・`dismiss`・`ask_decide`・`answer`。値は画面のボタンの名前を変えても変わらない（R84）。

1. 処理を始める時点の `applied_ops` に無い op を集める（`dismiss` と、それを指す `undo` は窓口が反映する op ではないので除く）。実行する前に、その中の `undo` が指す op を先に外す: 指す先が同じ未反映の中にあれば、両方とも実行せず反映済みにする（取り消した決定を一度実行してから戻す、を起こさない）
2. 残った op を op_id の順に処理する
3. `item_id` が空の `repeat` と、停止の行への `answer` はカードを持たないので、この照合をせずに 4 の手順で処理する。ほかの操作で `item_rev` が今の `rev` と違うものは適用しない（画面も断るが、ログに残ったものがあれば）。カードを見直して `rev` を上げ、出し直す（op_id は `applied_ops` に入れる）
4. type ごとに反映する。片付けたカードは `state: "done"`・`resolved_by: "user"`・`resolved_at`（と `resolved_option`・`resolved_text`）にする
   - `decide`: `option_id` の選択肢で作業を進める（判断・選択肢のある許可・送信前・停止）。決めたことを実行して状態が変わったら（マージした・入れた・送った）、カードの `why` の先頭に「結果: <何をしたか・今どうなっているか>」を 1 行足す。片付いたの列で、決めたときの状態が古いまま読まれるため（2026-11-16 に、マージ済みのカードが「まだ main に入っていない」と出ていた）
     - `option_id` が `other` のときは、`text` を深田の決定として扱う（停止の「別の回答」。判断・許可・確認・送信前の選択肢の外の答えは「直しを伝える」の本文つき `talk` で届く）。「もう済んだ」「手で送った」なら、その作業をメインはやらない。済んだ事実を確かめられるなら確かめる（Slack なら送られたメッセージを読む）。`resolved_option: "other"`・`resolved_text` に原文を残す
     - `text` が選択肢のどれかと同じ意味なら、その選択肢として進める。曖昧で進められないときだけ、カードを開いたまま深田に 1 問だけ聞く
   - `accept`: 確認の「承認」なら、その成果物のその版を承認として扱う。結んだタスクは、カードを閉じれば state.ts がカードの効果（references/schema.md の「タスクの今の決まり方」）で済か着手できると決めるので、手で `ok` を書き写さない（`effects` で `start` にしたタスクまで済にしないため）。カードに `elements` があれば、全番号の行き先を `element_map` に書き（新しく要るタスク・依頼の済の条件もこのとき作る）、op の取り込みと同じ書き込みで渡す。番号が 1 つでも欠けると書く道具が断る（references/cards.md の「承認の前に要素を固める」）。カードに `request_id` があれば、その依頼の `evidence` に `{ "when": <済の条件の番号>, "kind": "op", "ref": <op_id>, "card": "<カードの id>", "rev": <item_rev> }` を足す（版に結ぶので、成果物を改訂して `rev` を上げると古い承認は効かない）。許可の「許可」なら、`target` の操作を 1 回だけ行う。済になったタスクの見直し（schema.md の `tasks[]` の「済にしたら見直す」）は同じ書き込みで行う
   - `sent`（手作業の許可の「対応済みにする」）: `manual.check` で窓口が確かめてから閉じる。確かめて済んでいなければ、カードを開いたまま何が残っているかを `why` に書いて `rev` を上げる
   - `sent`: 「送信済みにする」「対応済みにする」。`awaiting` を書けるなら（返事を待つなら）`state: "waiting"` にして `awaiting`（`who`・`what`・`since`・`resumes`・`remind_at`）を書く。結んだタスクは state.ts が相手待ちと決める（カードの `tasks` がタスクを指すので、タスクに `wait` は書き写さない）。返事が要らなければ done にし、結んだタスクは着手できるになる
   - `skip`: 送信しない・返信不要・却下。done にする。許可を却下したなら、その操作はせず、ほかの作業を進める
   - `delegate`: 許したうえで、この案件の `scope` を以後は任せる。操作を行い、判断の記録に `kind: "permission"` で残す（references/rulings.md の「いつ書くか」）。以後、同じ `scope` の許可は出さない
   - `talk`（本文なし）: 深田がそのカードについて担当（担当が無ければ窓口）と話し始めた合図。会話は担当のチャットか窓口のチャットで行う。カードの中身は変えず、op を `applied_ops` に足すだけにする。カードは要対応に残り、窓に「協議中」と出る（件数は変わらない。references/schema.md の「協議中と修正の状態」）。話がまとまったら、担当の結果でカードを書き直して `rev` を上げる（相談なら判断・確認・送信前に書き換える）か、片付ける
     - `terminal` があるとき: 担当のいないカードで、窓が `consult --card` で相談のタブを立てた（か、開いていたタブを前に出した）印。会話はそのタブで行い、決まったことは返しで届く（references/consult.md の「カードの相談」）。反映は `applied_ops` に足すだけで同じ。協議中の印は、タブが Orca から消えると state.ts が外す。カードが片付いたらタブを閉じる（references/consult.md の「カードの相談」の 8）
   - `talk`（本文つき）: 「直しを伝える」（判断・許可・確認・送信前）で深田が書いた直しの指示（原文）。窓口がそのまま担当に送り（`orca orchestration send --to dispatch:<担当の今の Dispatch>`。担当がいなければ窓口が直す）、op を `applied_ops` に足すだけにする。受け取ったことをカードに書かない・`rev` を上げない（上げると直す前に私の番に戻る）。窓は「修正依頼済み（受領待ち）」→ 反映で「修正待ち」と出し、件数から外す。直した版ができたら `href`・`evidence` を新しい版に書き換えて `rev` を上げる（私の番に戻る）
   - `ack`: 報告の「既読にする」。done にする
   - `revert`: 報告の `done[target]`（0 始まり）を戻してほしい、という依頼。`target` は押したときの版の並びを指すので、同じカードへの revert は先に全部集めて対象の行を決め、行を外すのと `rev` を上げるのは最後に 1 回だけ行う（1 件ずつ外すと後の添字がずれる）。可逆で小さいもの（設定 1 か所など）はそのまま戻し、その行を `done` から外して、戻したことを新しい報告で知らせる。手戻りが大きいもの・ほかの作業に響くものは、戻すかどうかを判断にして出し直す
   - `repeat`（窓の上の「記録の再読を依頼」。パネルでは「前にも言った」）: 深田が、前に伝えたことをメインが落としたと感じて押したもの。`item_id` は空。発言の記録（`.orca/cockpit/utterances.jsonl`）と判断の記録を読み直し、落ちていた判断を references/rulings.md の「いつ書くか」の手順で書き、何を落としていたかを深田に 1〜2 行で返す。押下は hook が数え、2 回で次の日の最初の発言の前に新しいチャットへ引き継ぐ（references/resume.md）
   - `dismiss`（停止の票の「対応済みにする」）: Orca で止まったエージェント・worker の停止の票（窓が自動で出すもの。利用枠の上限で止まった、など）を、深田が片付けたとして消した印。`item_id` は `#agent:<session か terminal か worktree か title>` か `#dispatch:<task>`、`item_rev` は止まった時刻（ms）。窓口が反映する op ではなく、state.ts の未反映の数に入らない（その op_id を指す `undo` も同じ）ので、`applied_ops` に足さなくてよい。次にまた止まると時刻が変わり、票が出直す。止まった時刻が取れない票（`item_rev` が 0）には、このボタンは出ない
   - `ask_decide`（窓からの質問の「A で返す」「書いたことを窓口に返す」）: `item_id` は `#ask:<質問 id>`、`answer` はどの答えか（`{ at: 答えの時刻, head: 頭の 80 字, n: 控えの中の答えの通番 }`）。答えの【選べる案】から選んだら `choice`（`"A"` など）、書いて返したら `text`（深田の原文）を持ち、両方は持たない。どちらも無いのは前の形の「この答えを窓口に返す」で、そのまま読む。窓はこの op を書いてから、質問のタブに深田の言葉（`案 A で。` か書いた文）と、改行して `【相談の知らせ】返しを書いて（op <op_id>）` を 1 回で送る（前の形の op は知らせだけ）。同じ答えに同じ返し方の op は重ねず、違う案・違う文は新しい op になる（返しは op ごとに届くので、窓口は同じ答えへの最後の op の返しを使う）。窓口はこの op だけでは何も実行せず、`op` にこの op_id を持つ返しが届いたら references/consult.md の「窓から質問する」の手順で反映し、同じ書き込みで op_id を `applied_ops` に足す。返しが届かないあいだは `checks.unreflected_returns` が `{ ask, op, missing: ['返し'] }` で名指しする
   - `answer`（停止の行の「答える」「許可」で、窓が問いの主に答えを届けた記録。R222・R223）: `item_id` は行の id（`#agent:…` は端末の AskUserQuestion・許可の確認、`#ask:msg_…` は worker が orchestration で聞いた問い、`#cowork:<仕事 id>` は一緒に作る仕事の担当の返事待ち）、`item_rev` は聞いた時刻（ms）、`text` は深田の言葉の原文（選択肢を選んだときはその文。許可なら端末の選択肢の文で、`Yes` は今回だけ許した）、`via` は届け方（`keys` は端末に番号のキー、`reply` は `orchestration reply` で worker に返して宛先の Run にも写した、`dispatch` は担当の今の Dispatch に送った）、`to` は届け先、`keys` なら `key` は送った番号。窓は届けてから書くので、届け直さない（`reply` の写しは窓口の Run にも届いている）。判断にあたる言葉（方針・選んだ案・以後も許すなど）は references/rulings.md の「いつ書くか」で判断の記録に残し（`quote` に `text`）、タスクの作業が変わるなら担当か worker に伝え、op_id を `applied_ops` に足す。カードは無いので書き直さない
   - `undo`（1 で外れずに残ったもの = 反映済みの操作の取り消し）: 反映済みの決定を取り消したら「再判断」として扱う: 作業を戻すかを新しい判断（`rev` を上げる）にして出し直す。カードの効果で済になったタスクは、戻すと決めるまで済のまま残す（反映の前に取り消した承認は、窓口がカードを開いたままにするので効かない）
5. カード・タスク・依頼の変更と、反映した op_id（`applied_ops`）を、書く道具 `cockpit-write` の 1 回で渡す（references/schema.md の「書く道具」）。2 回に分けると、間に読んだ画面と hook が同じ op を未反映と数える。画面は反映済みの操作を重ねず、cockpit.json の `state` と `resolved_*` を正として表示する
