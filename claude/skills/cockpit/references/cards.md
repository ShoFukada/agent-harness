# カードの書き方

cockpit skill の SKILL.md から分けた細部。何を深田の番に出すかを決めるとき、判断・許可・送信前・確認・相談のカードを書くとき、hook に判断材料（context）や必須の欄が欠けていると指摘されたときに読む。欄の一覧と必須の欄は references/schema.md の「カード」と「必須の欄」。

人が読む日本語は ja-writing skill の規則で書く。画面の文言は業務文書の語調にし、内輪の語（「こっちボール」など）を使わない。

## 何を私の番に出すか
- 件数に数えるのは、停止・許可・判断・送信前・確認の 5 種類だけ。相談は要対応に並ぶが、深田に決めてもらうまで件数に数えない（R52）。受信・報告も数えない。深田が「担当と協議」を押したカードは「協議中」の印が付くだけで、数える種類なら件数に残る
- 深田に出す判断は 3 種に絞る（v40 で承認。R52）: 外に出るもの（顧客・社外への送信や資料）・戻せないもの（push・本番・データの変更）・要件や設計が変わるもの。戻せる小さな判断は、エージェントが決めて進め、報告に理由と戻し方を書く
  - 要件や設計が変わる判断で、案が分かれているものは判断にする。戻せない操作は許可にする。外に出る文面は送信前にする
  - 案がまだ分かれず、担当か窓口が深田と話して詰めたいことは相談にする（references/cards.md の「相談」）。無理に選択肢を作って判断にしない
- push のように繰り返す許可には `scope` を書き、深田が「この案件では一任する」を押したら以後は聞かない（references/ops.md の `delegate`）
- 顧客に聞くこと・返すことは送信前にする（版 1 の「聞く」）。送る本文そのものを `draft` に入れ、`format`（`slack`・`teams`・`mail`）の宛先の書式で書く。書式は dev-standards の決まり `rules/docs/message-formats.md`（references/cards.md の送信前の `draft`）
- それ以外（UI の細部、可逆な技術判断、作るかどうかの小さな判断）はエージェントが決め、報告の `done[]` に理由（`why`）と戻し方（`undo`）を添えてまとめる（U6）。報告に深田への問いを書かない。問いがあれば判断か確認にする（報告は件数に入らず、深田が気づかない）
- メインが自分で片付けたもの（worker の結果の取り込みなど）は要対応に出さず、`state: "done"`・`resolved_by: "owner"` で記録だけ残す
- ワークスペースの root を push するかは、`scope: "push"` の許可にする。その案件で一任されていれば出さない（選択肢の形・一任の見分け方・hook が出させる条件は references/cards.md の「push の許可」）

### 「確認」を出す範囲
深田に「確認」を出すのは次の 4 つだけ。成果物をすべて「確認」にすると、依頼の数だけ判断が増える。
- 社外に出るもの（顧客への資料・メール・提案）
- 設計・要件の文書
- マージ前の大きい変更
- 深田が確かめたいと言ったもの

それ以外の成果物はメインと Codex が見て、リンク付きの報告で知らせる。成果物が Drive にあるなら Drive の URL を、HTML のページなら公開した artifact の URL を、リポジトリのファイルならそのパスを `href` か `links` に入れる（リンクが無いと、深田は窓から成果物を開けない）。

### 確かめてもらう成果物は artifact で出す
- 深田に見てほしい HTML のページ（比較・説明・報告・調査のページ）は、artifact で公開し、カードとチャットには artifact の URL を書く。手元のファイルのパスだけで渡さない（深田は手元のパスを開けない）。担当や worker がページを作ったときは、1 つの HTML ファイルのパスを報告で受け取り、メインが公開する。一緒に作る仕事の担当は自分で公開し、最初の URL だけを送ってくる。メインはその URL をカードと帳簿に書き、直しのたびに出し直さない
- 一時フォルダ（`/tmp`・`/private/tmp`・scratchpad）のファイルを `href` にしない。深田の画面から開けず、消えることもある（hook も `checks.local_deliverables` で名指しする）。コードの差分は PR かリポジトリのファイルのリンクでよい（`diff`）
- 確認用のページは ja-writing skill の章立て（背景と前提 → 結論 → 図 → 各論 → 深田に確かめてほしいこと）にし、最後の「深田に確かめてほしいこと」を 2〜4 個書く。同じ点を確認の `look_for` にも書く。メインと Codex が確かめた結果は `evidence` に書く
- 深田に頼むこと・聞くこと（決めてほしい・見てほしい・許してほしい・switch などの手作業・顧客への確認）は、チャットに書くだけで済ませず、同じターンでカードにする。深田は窓だけ見て進める。返答に依頼や問いがあるのにそのターンで cockpit.json を書いていないと、メイン側の Stop の hook が 1 回止める

## 言葉づかい（R50）
深田の指摘（「言葉遣いがちょっと柔らかいかつ AI slop 感がある」）から決めた。窓口が書くカードの文（`title`・`purpose`・`why`・`next`・`context`・`fallback`・`look_for`・`evidence`）は次のとおり書く。
- 硬めの業務文書の語調にする。1 つのカードの中で体言止めと「です・ます」を混ぜない
- `title` は 20 字以内の「何を・どうする」。`why` は 1〜2 文、`next` は 1 文
- 使わない: 「〜しましょう」「〜してくださいね」「ぜひ」「お気軽に」「すべて片付きました！」のような労い・感嘆、「シームレス」「包括的」「強力な」「〜を実現」、同じ内容の言い換えの繰り返し、長い前置き
- 種類・ボタン・ラベルの名前は窓の画面の名前に合わせる（R84。業務の語調の名前: 停止・許可・判断・送信前・確認・受信、承認・直しを伝える・許可・この案件では一任する・却下・対応済みにする・送信済みにする・送信しない・返信不要・既読にする・担当と協議、協議中・修正待ち・報告（参照のみ））。カードの文の中でボタンを案内するときも、この名前で書く

例: 「ぜひご確認ください！窓の新しいデザインをシームレスに実現しました」ではなく、`title`「窓の版 3 を確認する」・`purpose`「3 タブの形で使えるかを決め、取り込みに進む」。

## 窓に出す情報（R102・R104）
深田が判断に使う情報と、負荷になる情報の決まり。深田のこれまでの指示（knowledge-harvest の inbox・判断の記録・発言の記録）から割り出した。カードを書いたら、この 16 項目で読み直す。

出すもの:
- P1 何の話か・何のためかを、初めて聞く前提で先頭に置く。`purpose` は題の直下に出る
- P2 文章の説明ではなく、具体例・実物・並べた比較で見せる（`example`・`compare`・`figure`・`draft`・`quote`）
- P3 どの仕事・どのタスクの話かを上にたどれるようにする（`stream`・`tasks`）
- P4 おすすめの案を先に置く（`recommended`）。選択肢以外の答えと直しの指示は「直しを伝える」で返るので、選択肢を足して埋めない
- P5 確認は、何を・どこで・どの観点で見るかに絞り（`look_for` 1〜3）、実際の差分を見せる（`diff`）
- P6 実物へ 1 回の操作で届くようにする（開くリンク・コピーできるコマンド）
- P7 原文と根拠をたどれるようにする（依頼の原文 `request`・相手の発言 `quote`・確かめた結果 `evidence`）
- P8 どこまで進み、何を待ち、深田の指示がどうなったかが分かるようにする（state.ts が事実から決めるタスクの状態と待ちの 1 行、仕事の状況の文 `status`、協議中・修正待ちの印）

出さないもの:
- N1 深田が決めなくてよいことはカードにしない。決めて進めた結果は報告で共有する。一任された操作（この案件の push・マージなど）の許可は出さない。一任されたと見なすのは、深田が「この案件では一任する」を押して窓口が記録した `permission`（references/ops.md の `delegate`）か、原文で今後の分まで任されたと読める `permission` が、`compaction-keep.py rulings <root>` に同じ `scope` で有効なときだけ。「今回だけ push して」のような 1 回の許可は一任に数えない
- N2 見るはずのない情報・済んだもの・作り手側の知らせを並べない。細部（commit の一覧・テストの件数・経緯の長文）は「詳細」か `links` に置く
- N3 説明の無い数字・記号・ボタンを出さない（「26/34」「記録の再読を依頼」）
- N4 文章で説明せず、画面の形（並び・位置・印）で分からせる。カードの文に画面の使い方を書かない
- N5 内部の言葉と、別の場所を指す呼び方を使わない（「案 A」「上の件」・判断の記録の番号）
- N6 凡例・色・飾りを増やさない（図の色は `currentColor`）
- N7 同じ事実を 2 か所に持たない（references/schema.md の「同じ内容を 2 か所に持たない」）
- N8 窓口・担当の都合での先送り（「12 月に進めてよいか」「落ち着いてから着手でよいか」）を判断のカードにして深田に回さない。今進めるか、順番を決めて今の枠に入れる。待つのは外の理由があるときだけで、外の相手や出来事はタスクの `wait` に書き、深田を待つものはカードから指す（R193。書き方は references/schema.md の `tasks[]` の `wait`）

番号と一覧の 1 行:
- カードの文（`title`・`purpose`・`why`・`context`・`fallback`・`look_for`・`evidence`・`body` など）に判断の記録の番号（「（R46・R47）」）を書かない。窓からは開けない場所を指す呼び方になるため（N5）。判断の中身が要るなら平文で 1 文書く。番号は窓口との会話・ページ・作業メモで使う。カードの id（`d3`）は窓に出るので、文の中で使ってよい
- 判断の一覧の 1 行には「おすすめ: <選択肢の `label`>」が出る。`label` は単独で意味の通る短い名前にする

## 書き方
- タイトルは「何を」「どうする」の 1 行。「案 A」「上の件」のように別の場所を指す呼び方をしない
- 種類ごとの必須の欄（references/schema.md の「必須の欄」）がそろわないカードは窓に出ない。出す前にそろえ、hook に `incomplete_cards` で名指しされたらその場で埋める。`at` から 30 分たっても欠けていると、深田の窓の「帳簿の未記入」に出る
- 票を開いて最初に見えるのは、題の直下の `purpose` 1 行と、種類ごとに下の表で示す部分だけで、残りは畳んだ「詳細」に入る。最初に見える部分だけで返答できるように書く。どの種類も `why`・`fallback`・`background`・出典は「詳細」に入る

| 種類 | 最初に見える部分（上から） | 返答 | 「詳細」に入るもの |
|---|---|---|---|
| 判断 | `context.what`・選択肢（おすすめが先頭、各案に `example` 1 行）・`compare` か `figure`・`context.gain`・`context.cost` | 推奨案で決定・選択肢を選択・直しを伝える | `context.now`・`context.how` |
| 許可 | `effect`・`target`（平文 1〜2 行）・`undo`（選択肢があれば並べる） | 許可・この案件では一任する・直しを伝える・却下 | `context`・対象の細部 |
| 許可（手作業） | `manual.where`・`manual.command`（コピーのボタン付き）・`manual.steps`・`manual.check`（済ませたあと） | 対応済みにする・直しを伝える | なし |
| 確認 | 成果物を開くボタン（`href`）と差分（`diff`）・`look_for`・`request`（2 行まで。続きは畳む）・頼んだ直しとその後の状態。`draft` があれば、コピーの見本と Slack・Teams・メールの書式でコピーするボタン | 承認・直しを伝える（文を書いて担当に届ける。担当と話す画面も開ける） | `evidence`・`elements` の 5 つ目以降 |
| 送信前 | `quote`（返信なら相手の発言の原文）・`draft` の宛先・経路・本文（全文） | コピーしてスレッドを開く・送信済みにする・直しを伝える・送信しない | 元のスレッド |
| 停止 | 止まったタスクと担当・`reason`（原文）・答えてほしいこと 1 行（`unblock`） | 答える | 試したこと |
| 相談 | `issue`・`stance`・`known`・`undecided`・相談のメモ（`consult/<カード id>.md`）と、そこで決まったこと | 担当と協議 | なし |
| 受信（全体のタブ） | `quote`（届いた原文の抜粋）・`asked`・`routed` | 返信不要・元の連絡を開く | なし |
| 報告（参照のみ） | 項目ごとに `done[].what`・`why`（どの候補から選んだか）・`undo` | 既読にする・戻させる（項目ごと） | なし |

- 要対応の行の先頭は、深田がすることを示す語（決める・承認・送る・答える・許可・再開・相談・協議・返信・見る）。一緒に作る仕事は、担当が返事を待っていれば「答える」、そうでなければ「確認」（R115・R145）
- 判断では、背景（`background`）は「詳細」に入る。比較（`compare`・`figure`）は選択肢の下に最初から見える
- 判断の `why` は「今決める理由」の 1〜2 行（いつまでに決めないと何が止まるか）
- 選択肢には `example` を書く。選んだら何が起きるかを、選択肢どうし同じ条件で比べた実際の値の 1 行で（例「30 件 → 5 人に 6 件ずつ」と「30 件 → 取られるまで残る」）。`recommended` をおすすめ 1 つに付ける。`body` は選択肢の理由
- 比べると分かるものには `compare` を付ける。既定は表 `{ "columns": ["", "朝の振り分け", "作る量"], "rows": [["自動で割り当てる", "無くなる", "+1 日"], ...] }`。表で書けない流れ・配置だけを図（`figure`）にする
- `background`: いきさつ 2〜3 行。`{ "text": "...", "quote": "「原文」発言者", "date": "2026-11-14" }`。原文を推測で作らない。手元に原文が無ければ `quote` を書かず、`links` にスレッドや管理表の行を入れる
- 判断には `fallback` を付ける（期限までに返事が無いとき、メインが何をするかを深田があらかじめ分かるようにするため）。既定は「<対象のタスク> は止めたまま、<独立した作業> を先に進めます」と、遅れたときに起きること。おすすめを自動で採るのは、深田が事前に任せた範囲（UI の細部・可逆な技術判断）だけで、そのときは採る日時と戻すときの手戻りを書く
- 判断・許可・送信前は「何のため」と「具体例」の両方を持つ。何のためは `purpose` と `stream`・`tasks`、具体例は選択肢の `example`・`compare`・`figure`・`quote`・`draft` の実際の値。片方が書けないカードは出さず、書けるまで調べる
- 判断を頼むカードは、出す時点で関係するタスク（`tasks`）・実物へのリンク（`links`）・おすすめの案（`recommended` と理由）をそろえる。深田に聞き返されてから足さない
- どの判断にも「直しを伝える」がある（選択肢に無い答えや「もう手で送った」のような済んだことを書いて送る）。選択肢に「自分で送る」「対応済み」を足して埋めなくてよい
- 送信前の `draft`: `{ "to": "先方の担当者", "via": "Slack・共有チャンネル", "format": "slack", "text": "<本文そのまま。改行も保つ>", "href": "<元のスレッドか下書きを置いた場所のリンク>" }`。画面では送る見た目に近い枠で表示し、`href` があれば「コピーしてスレッドを開く」になる
  - `text` は、長さ・敬語の度合いを reply-draft skill（`~/.config/nix-darwin/claude/skills/reply-draft/SKILL.md`）に合わせ、箇条書き・見出し・強調・リンクを `format` の宛先の書式で書く。書式は dev-standards の書式の決まり（`~/.claude/plugins/marketplaces/medurance-dev-standards/rules/docs/message-formats.md`） に従い、ここに写さない。窓の「コピー」はこの本文を宛先の書式のまま貼る
  - `format`（必須）は `text` を書いた宛先の書式: `slack`・`teams`・`mail`。`format` は `via`・`href` の宛先と合わせる（cockpit-write が照合し、本文も dev-standards の検査にかけて、合わなければ書かない。断られたら理由の行を直して書き直す）。Slack・Teams・メール以外の経路（LINE・チャットワークなど）は `via`・`href` で宛先が決まらず `format` の値がそのまま使われるので、プレーンテキストの `mail` にする。確認のカードの `draft` も `format` を持つ
- 許可の `target` は対象そのもの（commit の範囲・送る本文・書き換える行）を平文 1〜2 行で書く。commit の一覧・変えたファイル・テストの件数は `links` に置く。`effect` は何が変わるか、`undo` は戻し方の手順
- 確認の `request` は深田の依頼の原文、`request_id` は依頼の帳簿の id（`r30`）、`look_for` は見てほしい点 1〜3（どこの何を、どの観点で）、`evidence` は確かめた結果（コマンドと結果・変わったところ）の文字列の配列。`evidence` を 1 つの文字列で書かない（書く道具が断る）
- 確認の `diff`（任意）: 差分のある成果物（コード・決まりの文書）なら、差分を開くリンク（PR の Files・compare の URL）を書く。要約だけで実物の差分を開けない確認にしない
- 送信前の `quote`（任意）: 返信なら、相手が聞いたことの原文 1〜3 行を書く。開かなくても何への返事かが分かるようにする。受信でも、届いた原文の抜粋を `quote` に書く
- 報告の `done[].why`（任意）: どの候補から選んだかを 1 文で書く（「候補は A・B で、B は手間が倍」）
- 停止の `reason` は、「エラー」の一語にせず、エラーの最後の数行か担当の質問の文をそのまま書く
- 成果物を改訂したら、確認の `href`・`evidence` を新しい版に書き換えて `rev` を上げる。古い版への「承認」は新しい版の承認にならない
- 並びのある説明（見る順番・手順・理由の列挙）は 1 段落に詰めず、改行と箇条（`- `・`1. `）で書く。`why`・`body`・`background.text`・`effect` で、改行・箇条・URL・`#123`（`repo` があれば PR）が画面で描かれる
- 資料（PR・Drive・設計書）は `links[]` に入れる
- 一度深田が答えたこと・自明なことをカードにしない。過去の決定は判断の記録と片付いたカードを探してから出す
- 図は SVG を `.orca/cockpit/figures/<name>.svg` に置いて `figure` から指す（JSON を軽く保つため）。色は `currentColor` を基本にし、script や外部の参照を入れない（画面が取り除く）。`viewBox` の幅は 480 以下にし、字は `font-size` 14 以上で描く
- 細かい数字・内訳・説明の文を増やさない

## 判断材料（context）
判断には `context` の 5 欄を埋める（空の欄は hook が `checks.missing_context` で名指しする）。深田がその話題を初めて聞く前提で書き、略語・内輪の呼び名・作業中に付けた記号を使わない。どれも文字列で、改行と「- 」の箇条を使ってよい。

| 欄 | 画面の見出し | 書くこと |
|---|---|---|
| `what` | これは何か | 誰が作った何で、何をするものか。具体例を 1 つ |
| `now` | 今どうなっているか | 今のハーネス・案件での扱いと、困っていること |
| `how` | 入れるならどうするか | 手順・触るファイル・手間・戻し方 |
| `gain` | 得られること | 深田の作業のどの場面で何が変わるか |
| `cost` | 失うこと | 手間・リスク・外に出るもの |

```json
"context": {
  "what": "問い合わせを担当者に振り分ける方法。一覧画面に「担当者」の列を置くかが決まる。\n例: 月曜の朝に 30 件たまっているとき、誰がどれを受け持つか",
  "now": "- 毎朝 9 時に主任が全件を見て、5 人に手で振り分けている\n- 振り分けが終わるまで誰も着手できず、毎朝 30〜40 分かかる",
  "how": "- 一覧画面に担当者の列を足し、件数の少ない人に割り当てる\n- 触るのは docs/design/一覧画面.md と割り当ての処理。実装は約 1 日\n- やめるときは割り当てを止め、列を空欄にすれば今と同じ",
  "gain": "朝の振り分けが無くなり、担当者は出社してすぐ着手できる",
  "cost": "- 実装が約 1 日増える\n- 得意な人に回したい問い合わせも件数で均等に配られる"
}
```

- 調べないと書けない欄があるなら、出す前に researcher に調べさせる（会話に依存しない調査は researcher、会話の文脈が要るものは fork）。推し量りで埋めない
- 書いたら、5 欄だけで「これは何？」「どう入る？」「何が良くて何が悪い？」に答えられるかを読み直す。答えられなければ足す
- 空の欄があると、hook が `checks.missing_context` で名指しする。空のまま出さない

## 承認の前に要素を固める
提案・設計・計画のように、中身が複数の要素から成るものを判断・確認で出すときは、出す時点でそのカードに `elements[]` を書く。承認したあと、どの要素をどのタスク・依頼に結んだかを取り違えないため。

```json
"elements": [
  { "n": 1, "text": "要対応の右の詳細を常に開く" },
  { "n": 2, "text": "担当と話したカードは要対応に残し、協議中の印を付ける" }
]
```

- 提案のページの「要素の一覧」は、この欄から作る。ページとカードで番号をそろえる
- 要素を変えたら `rev` を上げる（古い版への承認は効かない）
- 「承認」（`accept`）を取り込むときは、全番号ぶんの `element_map[]` を同じ書き込みで足す（references/ops.md の `accept`）。行き先は `{ "n": 1, "task": "t80" }`（タスク）・`{ "n": 2, "request": "r30#2" }`（依頼とその完了条件の番号）・`{ "n": 3, "skip": "<結ばない理由>" }` のどれか。足りない番号があると書く道具が断り、足りない番号を返す
- 承認の op が来たのに `element_map` が欠けたカードは、hook が `checks.unmapped_elements` で名指しする

## 相談（consult）
案がまだ分かれておらず、担当（か窓口）が深田と話して詰めたいときに出す。選択肢を無理に作って判断にしない。版 2 の協議中（`talk`）のカードは無くなり、相談に置き換わった。

```json
{ "id": "q3", "rev": 1, "kind": "consult", "title": "窓の凡例の減らし方を相談する", "state": "open",
  "at": "2026-11-22T10:00:00+09:00", "due": "2026-11-23", "stream": "s7", "owner": "o2",
  "purpose": "凡例の形が決まり、窓の作り直しを進められる", "fallback": "凡例は今のまま、ほかの直しを先に進める",
  "issue": "要対応のタブに凡例を何個まで出すか",
  "stance": "種類 6 つと手作業だけにし、数は出さない案が良いと考えている",
  "known": ["今は 10 枚のラベルが常に上に並ぶ"], "undecided": ["工程の凡例を全体のタブだけに置くか"],
  "links": [{ "label": "画面の案", "href": "https://claude.ai/code/artifact/..." }] }
```

- `issue` は何を決めたいかの 1 行、`stance` は担当の今の考え。`known`・`undecided` は箇条の文字列
- 相談は要対応に並ぶが、件数には数えない（深田に決めてもらうまで。R52）。深田が「担当と協議」を押すと「協議中」の印が付く。話がまとまったら判断・確認・送信前に書き換えて `rev` を上げるか、片付ける

## 深田の手作業を頼む
switch・プラグインの承認・ログイン・sudo のように、深田の手でしかできない操作を頼むときは、許可のカードに `manual` を付ける。深田は窓だけを見て、写して貼って「対応済みにする」を押せば終わる形にする（コマンドを文に埋めると、深田が探す手間を負う）。

```json
"manual": {
  "where": "ターミナル（どのフォルダでもよい）",
  "command": "sudo darwin-rebuild switch --flake ~/.config/nix-darwin",
  "steps": ["パスワードを聞かれたら Mac のログインのパスワードを入れる", "最後に エラーが出ずに終わったら「対応済みにする」を押す"],
  "check": "窓口が launchctl list で org.nixos.worktree-sweep が入ったかを確かめる"
}
```

- `command` は、そのまま貼れば動く 1 行（複数あるなら改行で区切る）。`~` やパスを省かず、確かめたコマンドを書く。画面はコピーのボタンを付けて目立たせる
- `steps` は、コマンドの前後で深田がすること（聞かれること・終わりの見分け方）を 1〜3 個
- `check` は、済んだあと窓口が何で確かめるか。「対応済みにする」が押されたら、窓口がこれで確かめてからカードを閉じる
- 手作業のカードは、何のため（`purpose`）と `manual` だけで済むように書き、`context` の長い文に手順を埋めない。`purpose` には、初めて聞いても分かるように何のための操作かを 1〜2 行で書く
- 1 枚に 1 つの操作にする。switch・再認証・リポジトリの片付けのように別々の操作を 1 枚に束ねない（束ねると、どれが何の操作かを深田が聞き返すことになる）
- 押す前に窓口が代われないか（CLI・API で済まないか）を先に試す

## push の許可
- その案件で push が一任されていれば（上の N1）、このカードは出さず、窓口が深田の変更も含めて中身を確認して commit・push し、報告に書く
- 一任されていなければ、ワークスペースの root を push するかは `scope: "push"` の許可にする。選択肢の id は、今夜の分だけ・深田の変更も含める・今は push しない（`later`）の形にする（選択肢があると画面は判断のボタンで出す）。進行中のタスクが無いのに root に未 push の commit か未 commit の変更が残っていると、メイン側の hook が発言のたびにこのカードを出させる（開いている間と、`later` を選んで 12 時間は出さない）。push の出し忘れを防ぐため
