# なぜ三者で回すか
Neon は視野が広く筋の違う仮説を出すが、細部を落とす。Astra は細部を掘って穴を見つけるが、指摘が多すぎて真ん中が引きずられる。性格が逆の 2 つに交互に聞き、真ん中の Claude が採否を決めると、どちらか一方に寄らない位置に落ち着く（外部で紹介されていた「Neon → Mythos → Astra」の往復を、深田が採った）。

要は、相手の答えを書き直さずに渡すこと。メインが要約し直すたびに細部が落ち、受け取ったモデルは「誰が何を言ったか」で重みを付けられなくなる（CLAUDE.md の「深田が言ったことは要約し直さず、原文を引用で渡す」を、相手のモデルの答えにも広げる）。

# 回す場面
- 回す: 影響の大きい設計に着手する前、同じ問題の修正が 2 回失敗したとき（codex-review の「呼ぶ条件」1 の前提の洗い出しに Neon の仮説を足す）、提案書・定例資料の骨子
- 回さない: commit 前の差分レビュー（今の codex-review の Astra だけ）、コードを書く・直す（Neon に書かせない）、日本語の仕上げ（ja-writing の polish.py）

# 渡し方
- 問いは話者ラベル付きの原文で組む。深田の発言は「深田:」、自分の案は「進行役:」、相手の答えは「Neon:」「Astra:」を頭に付けて貼る。決めた経緯（判断の記録の ID と原文）も同じく原文で入れる
- 相手の答えは書き写さない。出力のファイルを `cat` でつないで次の問いのファイルにする（書き写すと出力トークンを使い、書き換えも起きる）
- Astra への問いの末尾に「壊れるシナリオが具体的でない指摘は挙げなくてよい」と書く
- 問いの冒頭に「ファイルは読むだけで、書かない。コマンドで別の AI を呼び出さない」と書く。問いは自己完結で書く（目的・対象ファイルの絶対パス・聞きたいこと・期待する出力の形と長さ）
- 問いには、どこから起動された相談かを書かない。自分の名前やモデル名（Claude・Opus など）を話者ラベルや前置きに出さず、「Claude Code から」「エージェントから起動された」「サブエージェント」「`claude -p`」のような起動元の説明も入れない（判断の記録 R29。Antigravity の FAQ が、agy を第三者のコーディングエージェントで包む使い方を個人プランの対象外としているため）。相談の題材として Claude の設定やコードを扱うのは構わない
- Astra は起動元を知らされて動く（codex-review の prompt の冒頭）ので、Astra の答えを Neon への問いにつなぐ前に `grep -n -i -E 'claude code|claude -p|サブエージェント|opus' <astra-out>` で確かめる。起動元に触れた行が出たら、その行だけを消してからつなぐ

問いのファイルの組み方（1 巡目に Astra へ渡すものの例）。ファイルは巡ごとに番号を付けて分け、上書きしない（あとで深田に渡す記録になる）:

```bash
S=<scratchpad>/relay
cat $S/head.md $S/neon-out-1.md $S/ask-astra.md > $S/astra-prompt-1.md
# 2 巡目: Neon へは astra-out-1.md と 1 巡目の採否（不採用の理由 1 行）を、Astra へは neon-out-2.md と同じ採否をつなぐ
cat $S/head-2.md $S/neon-out-2.md $S/rulings-1.md $S/ask-astra.md > $S/astra-prompt-2.md
```

# 呼び方
どちらもメイン（Claude の sandbox の外）から呼ぶ。neon-ro はまだ worker の sandbox から出していないので、worker はこの skill を使わず、メインに頼む。

```bash
# Neon。cwd は使い捨ての空ディレクトリ、<リポジトリ> だけを読める。答えは <out>、ログは <out>.log
/Users/fukadasho/.config/agent-harness/claude/bin/neon-ro <リポジトリの絶対パス> <scratchpad>/relay/neon-prompt-1.md <scratchpad>/relay/neon-out-1.md
# Astra。codex-review skill の「呼び方」の main 側（codex exec -m gpt-6.2-astra -s read-only）。2 巡目は session id で resume する
```

- 対象が git の外のフォルダ（相談スレッドの案件フォルダ ~/work/<案件> など。提案書の骨子で起きる）のときは、`codex exec` に `--skip-git-repo-check` を足す。付けないと codex が起動の確かめで止まる
- どちらも数分かかるので Bash の `run_in_background` で走らせ、完了の知らせを待つ
- 失敗したら（認証切れ・枠切れ・timeout）リトライし続けず、そこまでの答えのパスを添えて「往復は未完了」と深田に戻す

# 回し方
1 巡は「Neon に 1 回、Astra に 1 回」。2 巡まで回す（Neon 2 回・Astra 2 回）。

1. Neon に聞く（neon-ro）: 状況・制約・深田の発言の原文と自分の案を渡し、視点と仮説、前提を疑う案を出させる
2. Neon の答えを原文で添えて Astra に聞く: 穴と反例、壊れるシナリオを出させる
3. 自分で採否を決める。決め方は codex-review の「指摘の採り方」1〜3 をそのまま使い、Neon の指摘にも当てる（Neon の賛成の返事は根拠にしない。拾うのは反対の意見と仮説）
4. 重い指摘が残ったら、2 巡目へ。Astra の答えと 3 の採否を原文で Neon に戻し、Neon の答えを添えて Astra にもう一度聞く

認証・権限・課金・データモデル・公開 API・不可逆なインフラの設計（codex-review の「呼ぶ条件」4）は、1 巡目を Neon と Astra に別々に聞き（どちらにも自分の案と相手の答えを見せない）、2 巡目から相手の答えを渡す。Astra の独立した案を残すため。

# 止め方
- 重い指摘（壊れるシナリオが具体的で、この環境の運用で実際に起き、直す手間が防げるリスクに見合うもの）が残らなければ、そこで止める
- 2 巡したら止める。3 巡目は回さない
- Neon と Astra の意見が前提から割れたら（例: Neon は「そもそも作らない案」、Astra は「作るなら境界の穴が 3 つ」）、2 巡を待たずにその場で止める。前提を決めるのは深田

# 深田に渡すもの
- 結論 1〜3 文
- 採った指摘と採らなかった指摘（どちらの指摘か・理由 1 行）
- 割れた点と、双方の答えのファイルのパス（Neon・Astra の out を巡ごとに）
- 回した巡の数（「1 巡で止めた: 重い指摘なし」など）

決めるのは深田。往復は判断の材料を作るためで、結論を作って先に進めるためではない。
