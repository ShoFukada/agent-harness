# 書き方の規則
結論を先に、1 段落 1 つの主張で書く。答える前に問いが何個混ざっているかを分け、各論点の結論は、何が起きうるか・どう手を打つか・それで足りるか、の 3 文以内にする。箇条書きは項目が並列・順序付き・比較のときだけ使い、入れ子にしない。平易な語と具体例、能動態で書き、読み手の前提知識に合わせて専門語を減らす。

文の組み立て方:
- 採った案・決めたこと・起きたことだけを書く。「X ではなく Y」の対比は、X が実際に検討されて読み手がその結果を必要とするときだけ使う
- 本文はやることから始める。前置き・分類の説明・結びの総括は、本文で言えている状態にして削る
- 事実と具体例で書く。接続句・強調・自作の複合語ラベル・比喩は、言い切れる語に置き換える
- 数字には基準（いつ時点・何の日付）・単位・数えた対象を書く。合計と内訳が合わない数字は、合うところまで分けて示す
- 日本語と英数字の間に半角の空白を入れない（3件・22:00に・mainに入れる・IDで指す・Neonが見る）。ページの見た目の間隔はCSSの`text-autospace`で付ける。空白を残すのは、英数字どうしが並んで切れ目が消える所（未commit 1つ・Google Drive）と、コマンド・パス・SHA・ブランチ名の前後で、これらはコードの書式で囲む。書いた直後にja-review hookが、変えた行の詰める所を機械的に詰める
- 判断を求められたら一つに決めて書く。両論を並べるのは、ユーザーが決めると明示するときだけ
- 敬体か常体のどちらかで一つの文書を通す。日本語の語順で書き、主語は人か組織にする。文の長さに変化をつける
- 語彙は、新しく参加する同僚に説明する日本語にする。「正本を更新する」は「元のファイルを更新する」、「重要度を按分する」は「重要な指摘から確認する」のように、文脈に合う平易な文にする。硬い語の一覧と言い換え候補は dev-standards プラグインの hook（ja-vocab-lint）が持ち、当たった語を返す。直訳語・比喩動詞・カタカナ語・否定対比・絵文字・ダッシュ・連用形名詞は、書いた直後に ja-review hook が yomiyasu の lint で書いた行の候補を返す。意味や用語を担う表現は残してよい鉤括弧で引用した語・コード・専門語の説明には当てはめない
- 人や役割には所属を付け（「〇〇社の責任者」）、「予定」「記録」「次回」のような語は何のものかを言い切る。平易さより、事実として正確な語を選ぶ
- 平易にするのは、造語・社内だけで通じる語・漢語を重ねた語を避けるため。業界で普通に使う用語（参加荷主、損益分岐点、混載 など）は言い換えない
- 仕事の動作と成果物の語（業務の漢語にする範囲と言い換え）は、dev-standards の決まり（`rules/docs/writing.md`）に従う
- 文書やソフトウェアの version は「版」と書かず「バージョン」と書く（「承認した版」ではなく「承認したバージョン」、「最新版」は「最新バージョン」）。「初版」「確定版」「安定版」のような決まった言い方と、「Web 版」のような種類の違いを指す語はそのまま使う
- 語調は読み手で決める。読み手が分からないときは、書き始める前にユーザーに聞く

  | 読み手 | 例 | 語調 |
  |---|---|---|
  | 顧客・社外 | 提案資料・報告書・定義書・画面の文言・レポート・社外へのメール | 業務文書。常体か敬体のどちらかで通し、見出し・資料名・画面のラベルは名詞句にする。口語や子ども向けの言い回し（「いちばん安い」「下がる額」「〜がいい？」）にしない |
  | 社内 | 社内 Slack・社内向けメモ・Issue/PR 本文・議事録 | 丁寧語の平易な文。話し言葉寄りでよいが、崩しすぎない |
  | 個人の発信 | X の投稿・YouTube の台本・ブログ・友人への連絡 | 口語でよい。ユーザーの過去の文体に合わせる |
- Slack・Teams・メールの文面は、語調を読み手で、レイアウト（箇条書きの記号・見出し・強調・リンク）を宛先で決める。宛先の書式は dev-standards の決まり（`rules/docs/message-formats.md`。場所は reply-draft skill に書いてある）に従う
- 顧客・社外に渡す .md と .html には、読み手の印を付ける（Markdown は frontmatter の `audience: client`、HTML は `<meta name="audience" content="client">`）。仕上げの hook と polish.py はこの印を見て業務文書の語調にそろえる。印が無い文書は、宛名の「様」・御社・貴社や、提案・報告・定義書・操作マニュアルといった本文の手がかりで読み手を判断する
- 顧客に出す資料には、誰のどの判断のための資料かを 1 行の印で残す（Markdown は frontmatter の `purpose:`、HTML は `<meta name="purpose" content="...">`）。あとで直す・作り直すときに狙いを読めるようにするため
- 業務文書の語調（顧客・社外の読み手）:
  - 話し言葉の語を書き言葉にする。「いちばん」→「最も」、「ちゃんと」→「確実に」、「すごく」「とても」→ 程度を数値か「大幅に」で、「ざっくり」→「概算で」、「だいたい」→「おおむね」、「〜とか」→「〜など」、「〜けど」→「〜が」、「〜って」→「〜という」、文頭の「なので」→「そのため」、「〜しちゃう」→「〜してしまう」、「〜がいい？」→「〜が適切か」
  - 替えるのは話し言葉の語だけにする。「やる」→「行う」、「〜しちゃう」→「〜してしまう」のような口語の動詞は替える。実施・確認・対応・検討・承認のような業務文書で普通に使う漢語は、平易にするための言い換えの対象にしない
  - 語調を上げても、文の働き（相談・依頼・提案・報告・宣言）と言い切りの強さ（〜したい・〜できる・〜する）は変えない（「確かめたいです」を「確認いたします」にすると、相談が宣言に変わる）。文書の中で決めた用語・画面の文言・例の中身も言い換えない
  - 感嘆符・絵文字・相槌（「なるほど」「ですね！」）・内輪の略語を使わない。敬語は二重にしない（「おっしゃられる」→「おっしゃる」、「拝見させていただく」→「拝見する」）
  - 社外の特定の相手に敬体で書くときは、敬語を述語の働きで上げる。読み手への依頼と読み手の行為は尊敬語（確認してください→ご確認ください、来てください→お越しください）、読み手に向かう自分の行為は謙譲語（連絡します→ご連絡いたします）にし、自分だけで済む作業（直しました、行いました）は丁寧語のまま残す
  - 同じ相手への言い回しも上げる。「〜と助かります」→「〜いただけますと幸いです」、「申し訳ありません」→「申し訳ございません」、考えや気持ちの「〜ています」→「〜ております」、「どちらがよいか」→「どちらがよろしいか」。頼みの強さは変えず、原文に無い「させていただく」「恐れ入りますが」や、重い依頼の形（〜くださいますようお願い申し上げます）を足さない
  - 「教えてください」は、日程や名前のような事柄を尋ねるなら「お知らせください」、説明や手順を頼むなら「ご教示ください」にする
  - 深田が読み比べで選んだ言い回し（判断の記録 R229・R230・R231）:
    - スライド・資料の箇条書きは体言止めで締める（「反映済み」「登録中」「運用を開始」）。「〜の」を削って名詞を直につなぐ（本番運用・試作環境・API提供）。相手に決めてもらう事項の見出しは「ご判断いただきたいこと」
    - メールと連絡の箇条書きは、文なら句点を付ける。読み違えない所の読点と「の」は削る（「CSVを開発環境の取込画面で」）
    - 話し言葉の和語を業務の漢語にする: 進捗・試行期間・展開する・現行・算出される・反映される・承認基準・連携方法・閲覧する・異なる。ただし見出しの短い和語（作り直し・追う）は、意味が伝わるなら残す
    - 画面やシステムの動きは書き言葉の動詞で書く（表示される・作成される・保存する・動作する。「出る」「作られる」「置く」「動く」にしない）
    - 相手の操作は尊敬語に上げる（「予約できます」ではなく「ご予約いただけます」）。使い方の案内は「期間を選ぶと出力できます」のように操作と結果で書き、「選んでください」と命じない
    - 時刻は「10:00〜10:40」と数字で書く（「10時から10時40分まで」にしない）
    - 見積の前提は「〜という前提でお見積もりしております」と、何の前提かを書く
    - 因果と段取りは「〜により」「〜を経て」「〜したうえで」「〜に沿って」でつなぎ、選択肢は「または」でつなぐ
    - 完了の扱いは「〜をもって完了とします」と言い切る。確認の報告は「確認しました」
    - 依頼の結びは「〜いただけますと幸いです」にし、「〜と助かります」は使わない。原文に無い「お手数をおかけしますが」は足さない
  - メールの宛名・挨拶（お世話になっております）・結び（よろしくお願いいたします）・署名・クッション言葉（お手数ですが、恐れ入りますが）は、相手との関係を保つ書き方なので、前置きや決まり文句として削らない
  - 規程・契約書・仕様書の正式な語と文末（実施する、届出、〜しなければならない、〜するものとする、〜とする）は、平易な語に言い換えない。許可（〜してよい）・権限（〜できる）・義務の語も互いに替えない
- 英語で組み立てた文を訳した語を使わない。とくに「効く」は、work / effective / help / matter を日本語の短い述語に落とすと出やすい。「この設定が効く」ではなく「この設定で応答が 2 秒速くなる」のように、何がどう変わるかを書く。同じ仕組みで出る「静かに壊れる（silently）」「〜した瞬間（the moment）」「堅牢（robust）」「示唆（suggest）」も、起きることをそのまま書く
- 文の組み立ても英語に寄せない。「これが原因だ」の「これ」は、指す名詞が直前の文にあるときだけ使う（前の段落全体を this のように受けない）。前の文の名詞を同格で言い直すだけの文（「12件を選んだ。条件の似た12件だ。」）は最初の文に入れる。名詞化を入れ子にしない（「どう決めるか、その決め方自体が無い」ではなく「決める手順が無い」）
- 主語や目的語を省いてよいのは、直前の文がその語を言っているときだけ。段落や話題が変わった最初の文では、何についての話かを言い直す
- 読み手が考えてもいない否定を足さない（「〇〇ということではありません」「〇〇が目的ではない」）。見出しは名詞句にし、句読点を含む文にしない
- 決まり文句で場を締めない（「ここがポイントだ」「そういうことだ」「まさにそれだ」）。自問自答で区切らない（「なぜか。〜だからだ。」「理由は単純だ。」）。「速く、確実に。」のように短句を読点で並べて句点で締める標語の形を、見出し・UI の文言・本文のどこにも使わない。答えをそのまま書く

削る・載せないと指示されたとき:
- 消すと言われた項目は、最初から存在しなかった文書として仕上げる。項目・見出し・目次・図の凡例・索引まで、その項目を指す箇所を全部たどって消す
- 「対象外」「扱わない」「記載しない」「削除した」といった断り書きや、消した理由の注記は、ユーザーが断り書きを求めたときだけ書く。読み手がその項目を探して迷うと思うなら、書かずにユーザーに確認する
- 「A ではなく B にして」と言われたら、B だけを書く。A に触れる文は残さない
- 委任するときも同じで、prompt には「消した後の完成形」を書く

成果物ごとの規律:
- 顧客・利用者・社外に出す文書には、受け手が判断し行動するのに要ることだけを書く。社内の言葉と身内の前提、社内の暫定の作業手段、こちらの都合、作り手の断り書きは書かない。リスクは受け手の判断に要るものだけ書き、起きるか分からない懸念を先回りして並べない。返事は聞かれた範囲に絞り、聞かれていない訂正・作り直しの明示・未確定の日付・新しい論点は書かない（時期が決まっていなければ「対応しだい共有します」）。業務報告と会議の報告は、受け手に見せた・話したことだけを、中身が分かる粒度で書く
- 顧客に出す文書では、合意済み・案・未決を書き分ける。相手が決める事項には推奨を書かず、判断に要る情報だけを並べる（上の「一つに決めて書く」は、こちらが決める事項に限る）。ユーザーが中身を見ていない提案は、金額・時期・依頼を抜いて「整理中」とだけ書く
- 顧客に一度出した文書を直すときは、章立てと分類の数を保って指摘された箇所だけを直し、直す前に原本を手元に控える。顧客と共有中の表は今のセルを書き換えず日付つきの行で追記し、他人が作った資料は上書きせず新しいバージョンを横に作る
- 顧客への障害報告は、冒頭 1 文で止まったもの・影響の範囲・今の状態を書き、続けて「原因」「対応内容」「再発防止」の 3 見出しにする（doc-type は incident）。謝るのは実害の範囲に限り、相手側の要因は事実として並べる
- artifact や HTML のページで説明・報告・整理をまとめるとき、文書に図を入れるとき、ユーザーに見てほしいファイルのパスを書くときは [references/pages.md](references/pages.md) を読む（章立て・図の媒体と動き・開けるパスの書き方）

# 仕上げ（Gemini 4 Neon）
Claude の書く日本語は硬い語彙と詰め込んだ構造に寄る。学習系統の違うモデルに最後だけ読ませると、その癖が落ちる。仕上げ役は語彙と文の自然さだけを見て、内容と構成には手を入れない。深田に見せるページ・文書は、公開・送付の直前に仕上げを通す（Neon の使い所は CLAUDE.md）。

.md / .html / .txt と gh の Issue/PR 本文は、hook（ja-review）が Stop 時に同じ仕上げを自動でかけ、数値・コード・リンク・敬体と常体が変わっていないことを確かめたうえで直接書き換える。hook がかからない渡し方（Slack 文面・メール本文・チャット・artifact の公開だけ・Docs）は、下の手順で手で通す。顧客に渡す提案書・規程・メールの下書きには、`audience: client` とあわせて `doc-type:` も付ける。仕上げ役に渡す規則・文書の種類の決め方・hook が捨てる書き直し・polish.py の細部は [references/polish.md](references/polish.md) にある。

手で通すときは、本文を書き終えてから `python3 ~/.config/agent-harness/claude/skills/ja-writing/polish.py --diff <file>` で差分を取り、事実・数値・固有名詞・引用・識別子・敬体と常体・Markdown の構造が変わった所を戻し、採る部分だけを元ファイルに反映する。手順の全体と引数は references/polish.md の「手で通す手順」にある。
worker（sandbox の中）からは polish.py の agy が Google に届かないので、文章を `/tmp/claude-<uid>` の中に写し、`/Users/fukadasho/.config/agent-harness/claude/bin/neon-polish <file> --diff` を他のコマンドとつながずに 1 行で呼ぶ（引数は `--diff`・`--audience`・`--doc-type` だけ）。
顧客に出す文書は、仕上げに渡す前に相手の担当者になったつもりで一文ずつ読み、新たな質問が出る所・後退や手抜きに見える所・社内の事情が透ける所を直し、直した箇所を報告に並べる。

エージェント向けの指示文（rule・skill・CLAUDE.md・AGENTS.md・roles）を書き直したときも、commit の前に手で polish.py を通す。ja-review の hook は指示文にかけない（`is_instruction_file` で除いている。見出し・印など機械が読む文字列が変わるのを防ぐため）。採るのは語と文の自然さの直しだけで、和文と英数字の間の空白・見出し・機械が読む文字列・許可と禁止・条件の形（「と」を「や」にするなど）を変える直しは採らない。

使わない場面: コード、コードコメント、コミットメッセージ、300 字未満の短文（差分が誤差になり、確認の手間だけが残る）。
