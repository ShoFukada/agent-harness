# ページ・図・ファイルのパスの決まり

ja-writing の SKILL.md から分けた細部。artifact や HTML のページで説明・報告・整理をまとめるとき、文書に図を入れるとき、ユーザーに見てほしいファイルのパスを応答に書くときに読む。文の書き方は SKILL.md の「書き方の規則」が先にかかる。

## ページの章立て
- artifact や HTML のページで説明・報告・整理をまとめるときは、背景と前提（なぜこの話か、読み手が知らない業務や経緯）→ 結論 → 全体像の図 → 各論 → 未検証と残る判断、の順に章を立てる。全体像は粗い粒度の図 1 枚から始め、細かい一覧は後ろに回す。仕組み・流れ・as-is と to-be は inline SVG で描き、箇条書きで代えない。各論の主張には具体例を付ける（実際の値、画面のスクショ、入力と出力、ユーザーや顧客の発言の原文）。表には読み方を添える
- 各論は論点ごとに、先に図の形を選んで描き、その下に論点の答えを 1 行で書き、詳細は `<details>` に畳む。形は中身で選ぶ（処理の順番は流れ図、状態の移り変わりは状態遷移図、分類と内訳は木、案の比べは比較表、予定と経緯は時間軸、変更は前後の並置）。形の索引と写して使える SVG の見本は diagrams skill にあるので、描く前にそこから選ぶ。数値の推移や比べはグラフにし、作り方は dataviz skill に従う。仕上げに本文を隠し、図と 1 行だけで各論点が分かるか確かめる
- 画面や操作が関わる論点は、模式図より実際の画面のスクショを主にし、画面どうしの対応と動線を矢印や番号で示す
- 章立ては hook（page_outline.py）が書いた直後に確かめ、背景の章が無い・図が無いページを知らせる
- 章・項目・表の行・図・決めてほしいこと・確かめてほしいことに、短い ID を見える形で付ける（章と節は `3`・`3.2`、図は `図3`、表の行は `A1`、決めてほしいことは `D1`、確かめてほしいことは `Q1`）。深田が「D3 が〜」と ID で指して質問できるようにするため（R67、2026-11-21）。ID は本文より小さく薄い等幅の字で見出しや行の頭に置き、要素の `id` 属性にもして `#D3` で飛べるようにする。出し直しても同じものには同じ ID を保つ

## ページの幅
見出し・文章・表・図・カードは、1 つの同じ幅の列に並べる（R75。2026-11-21 に深田さんが求めた）。
- max-width はページ全体の列（`.wrap` など）に 1 つだけ掛ける。幅の目安は 1100px
- p・ul・ol・blockquote・節（section）・本文の枠（`.prose` など）には、別の max-width（ch・em・px）を掛けない。段落だけを 42em などに絞ると、見出しの線や表は列の幅まで伸び、文章だけがページの半分で折り返す
- hook（artifact-lint.py）が、書いた直後に 2 つの形を名指しする。1 つは、同じ列の見出しや表より狭い max-width で折り返す段落・リスト・blockquote と、それを包む枠。もう 1 つは、狭い枠に入った表・図・カードの並び。1 列の短い表のように意図して狭くするときは、その要素か枠に `data-narrow` 属性を付ける

経緯: 最初の決まりでは、節に掛けた 78ch で表がページの半分の幅に縛られたため、本文の幅を p・ul・ol・blockquote だけに掛けるとした。ところが段落だけが 42em で折り返す形が残り、R75 で 1 列にそろえる形に改めた。

## カードで囲まない
同じ種類の項目（直しの一覧・課題・タスク・変更点）は、カード（枠・影・角丸の箱）を並べず、行を細い線か余白で区切った一覧か表にする（R111。2026-11-21 に深田さんが「闇雲にカードで出るのうざいかも普通に一覧でよくない？線引いて」と求めた）。
- 1 件ずつ枠で囲まない。カードの中にカードや引用の箱を入れない。1 つの境目は、線・背景色・影のうち 1 つで示す
- 枠を使うのは、種類の違う中身を並べる要約と、入力欄・コードの塊だけ
- 見出しの上の英字の小見出し、状態を表さない札・色の点、絵文字のアイコンを置かない（AI slop の癖。調べは NN/g の Cards・GOV.UK の Summary list・Linear の 2026 年の刷新など）

## 見た目の確かめ（公開の前）
ページは、公開・見ての前に、書体・字の大きさ・レイアウト・色使いが AI の型どおり（AI slop）になっていないか、幅と明暗で崩れていないかを確認し、修正してから出す。誰が見るかは読み手で分ける（R138。2026-11-22 に深田さんが「neonは外しつつ、幅とかのやつとかは自身でチェックする感じで」と決めた）。文言の仕上げ（polish.py）は読み手によらず行う。
- 深田さんが内部で見るページ（報告・調査・比較・設計の artifact）: Neon には見せない。Claude が下の撮影をして、自分で確認する
- 窓の画面と、顧客・社外に出すページ・資料・図: Neon を主・Claude を副にして、下の手順をすべて行う
- 撮る: 幅 1280 と 400、明るいテーマと暗いテーマ。頭・図・表・長い本文を含める。画像は /tmp/claude-<uid> の中のフォルダに置く
- Neon（主。窓の画面と社外向けだけ）: `~/.config/agent-harness/claude/bin/neon-design-review <画像のフォルダ> --kind business`（他のコマンドと繋がず 1 行で）
- Claude（副）: 同じ画像を frontend-design skill と dev-standards の rules/dev/ui.md の基準で見る。AI の癖として、意味の無い色・装飾のグラデーション・左端の色の線・角丸の箱と札の並べすぎ・絵文字・見出しの大きさの段差の無さを探す
- 割れた点は理由で決め、直したら撮り直して採点し直す（2 巡まで）

## 図
- 図は読み手で媒体を分ける。人が読む文書（提案資料・設計書・README・手順書）の図は SVG で描き、本文と同じディレクトリか `images/` に .svg ファイルとして置いて `![]()` で参照する（本文への `<svg>` 直書きは GitHub が描画しない）。mermaid は AI が読む文書・一時的なメモ・PR 内の補助図に限る。SVG は配置・線の流れ・文字量を自分で決めてから描き、要素の多い図は Codex（Astra）に構成を相談してよい。描いた後は一度画像として開いて、重なり・はみ出し・読めない文字がないか確かめる（Neon に見せる手順は diagrams skill）
- 図と見出しは飾りで盛らず、強弱は線の太さと字の大きさ・太さで付ける

### 順序や流れが読み手に要る図
動きはユーザーが求めたときだけ入れ、順序や流れが読み手に要る図（データの流れ・処理の順番・状態遷移）は、SVG の中の CSS アニメーションで動かしてよい。JS を使わないので `![]()` で参照しても動く。構成を並べただけの図は動かさない。

- PDF・印刷・Google Docs・スライドでは止まるので、止まった状態だけで図が読めるように描き、動きは「どの順に流れるか」を足すだけにする
- `prefers-reduced-motion` で止める指定を入れる
- 見本は ja-writing のフォルダの `animated-diagram.svg`
- 確かめるときは `document.getAnimations()` で時刻を固定して数コマ撮り、順番どおりに動くかを見る

## 見てほしいファイルのパス
- 人間に見てほしいファイルは、Markdown のリンク記法 `[短い名前](絶対パス)` で書く。表示はラベルだけになるので、長いパスでも折り返さず、Orca で Cmd+クリックして開ける。ラベルはファイル名か用途の短い日本語。1 つずつリンクにし、ディレクトリだけ書いてファイルを省略しない。行を指すなら `path:line`
- 生のパスは、折り返すもの・Orca 管理外で日本語を含むもの・ディレクトリを含まないファイル名・直後に `:` と文字が続くものは開けない。開けないものは `orca file open --worktree <selector>` で直接開く
