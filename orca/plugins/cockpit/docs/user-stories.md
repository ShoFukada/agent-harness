# 操縦席のユーザーストーリー

利用者は受託開発の TL と PM を兼ね、10 本前後の案件を同時に動かす。案件ごとに Orca のワークスペース（本線）があり、本線のメインのエージェントが worker を 3〜8 本立てる。ディスプレイは 3 枚で、真ん中に Orca、左にエージェント、右に GitHub やファイルを置く。

操縦席は、利用者の脳を判断にだけ使うための画面。Orca の右のサイドバーのパネル（Orca の中の 1 案件）と、左のディスプレイの上半分に置くブラウザの窓（全案件）の 2 か所に出す。中身と操作は同じコードで、窓は Orca の外にある広さを使って全案件を並べる。

## 設計の原則
ストーリーと画面の要素は、どれもこの 5 つのどれかに結び付ける。結び付かない要素は削る候補にする。

### P1 抽象と具体を上下に並べ、つなぐ
> 整理・説明・計画・ヒアリングでは、抽象（目的・方針・論点）と具体（タスク・事例・実際の値）を分けて上下の階層に並べ、上と下がつながっているかを確かめる。（作者がエージェントに渡している共通の決まり「判断」）

- 階層は「全案件 → 案件（件数・期限・次の節目）→ 大タスク（元の案件。データは `streams`）→ タスク → 判断・具体例・実際の値・原文」。上から開けば必ず具体に届き、どの具体からも何のためかが 1 行で見え、1 クリックで上の層に戻れる
- 判断は「関係するタスク（何のため）」と「具体例（実際の値・図・原文）」の両方を持つ（skill で書かせる）
- どのタスクにもつながらない判断、どのくくりにも入らないタスクは「つながりなし」と出す。メインが直す合図

### P2 認知負荷を最小にする
> 「僕の脳リソースは有限であり細かいあれこれをひたすら管理したり意思決定はできない」「ちょっと多すぎる、こんなにあっても流石に管理できない」「なんかわかりづらいしなんのためにあるのかもよく」（11-11）「黒だと入ってこない」（11-16）

- 開いたときに見えるのは、決の件数といちばん急ぐ 1 件まで。残りは 1 クリック奥
- 数字は判断を変えるものだけ（件数・期限・止まっている数）。内訳・割合・細かい時間は出さない
- 何もしなくてよいときは「何もしなくてよい」と出し、安心して目を離せるようにする
- 同じ情報を 2 か所に出さない
- 色は意味だけに使い、形と文字でも示す。白地。読む順は上から 5 秒・1 分・決めるときだけ

### P3 決める・任せる・知らせるの線引き
> 「あなたの方で決められることは決めておいて、その内容をしっかり共有する」

- エージェントが決めたことは、理由と戻し方を付けて報告の項目に出し、利用者は違うものだけ「戻して」と返す
- 利用者が決めるのは設計判断と、設計書・要件の変更。返事が無いときは対象を止めたまま他を進める
- 一度答えたこと・自明なことは聞かない

### P4 速く戻れる・取りこぼさない
- 離席から戻ったとき・案件を切り替えたとき・定例の前後に、それぞれ要るものだけが出る
- 止まった worker と理由が見える（11/11 に落ちた 7 本が 11/16 まで止まっていた）
- 片付けたものは残から消えるが、読み返せる

### P5 軽さ
- 常駐のプロセスは 1 つで、メモリと CPU を食わない。Orca の状態はイベントとファイルの変更で取り、確かめに行くのは窓が表示されている間だけ
- 重さは体験の一部として扱う

## ストーリー
場面はプロファイル（会話履歴の圧縮）の 1〜11。各ストーリーの括弧は結び付く原則。

### S1 朝いちばんに、全案件の判断待ちを知る（P2・P4）
朝いちばんのとき、どの案件に自分の判断待ちが何件あり、どれが一番急ぐかを一目で知りたい。今は案件ごとに本線を開いて「進捗は？」と聞いている。

受入の条件
- 窓の上に、全案件のあなたの番の件数・止まっている worker の数・いちばん急ぐ 1 件が出る。件数はここと列にだけ出し、タブには出さない。押すとその案件のその項目が開く
- あなたの番の件数といちばん急ぐ 1 件は、決める・聞く・見て（承認の要る成果物）だけで数え、「あなたの番 15 件（決める 9・聞く 4・見て 2）」と内訳も出す（上の帯・列・パネルで同じ）。エージェントからの報告は件数に入れず、要対応の一覧で関係する大タスクのまとまりの最後に並べる
- 左の列に、操縦席のある本線だけが並ぶ。worker の worktree は行にせず、親の行に数だけ出す
- 各行に 名前・あなたの番の件数・最短の期限・止まっている数。手当てが要る行が上。メインが書く要約の文は出さない（隣の件数・期限と食い違いうるため。2026-11-16 に「期限切れ」の真下に「期限切れは 0 件」と出た）
- 何もしなくてよい案件は列の下に「何もしなくてよい n 件」として畳む。全案件で何もないときは「全案件 何もしなくてよい」と出る

### S2 案件を切り替えたときに、5 秒で現在地をつかむ（P1・P2）
Orca で別の案件に移ったとき、その案件の現在地（次の節目・判断待ち・止まっているもの）を 5 秒でつかみたい。今は「pj把握して」と頼み、要約を待っている。

受入の条件
- 窓の右は、Orca の前面のワークスペースに合わせて切り替わる。前面が worker の worktree なら、親の本線の操縦席を出す
- 列で別の行を押したら、次に Orca の前面が変わるまでその行を出す。いまどちらか（Orca で表示中／固定中）が分かり、「Orca に合わせる」と「Orca で開く」がある
- 案件の状態（依頼・タスク・worker・件数・期限）は、窓・パネル・hook・メインが同じ判定（src/state.ts）から読み、どの場所も同じことを言う
- Orca の操縦席のプラグインが承認待ち・止まっていて切り替えられないときは、その理由が窓の上に出る

### S3 定例の直前に、宿題と聞くことをそろえる（P1・P4）
定例の直前に、前回の宿題がすべて片付いたかと、顧客に聞くことを知りたい。今は議事録を読み直させている（「何が出たか忘れたけど」）。

受入の条件
- 「全体」で大タスクが手当ての要る順のまとまり（要対応あり・止まっている・外部待ち・進行中・未着手・完了）に並び、行ごとに今の様子と次の作業・工程の進みが 1 行で読める。外部待ちは「佐藤さん（認証情報）の返事待ち（11/17 から）。次: …」のように、誰の何を待っていていつからかが出る。次の節目（近い順に 3 件・あと何日）も見える
- 聞き方を承認した問いは全体タブの「顧客への確認」に並ぶ。まだ聞いていないものは「確認予定（聞き方を承認 11/16）」とどの定例で聞くか、メインが実際に聞いた（`asked_at` がある）ものだけ「回答待ち（11/21 から）」と出る
- 「あなたの番」の聞の項目に、聞き方と関係するタスクが出る

### S4 定例の直後に、出た判断を残に入れて追う（P1・P3）
定例の直後に、出た TODO と判断を残に入れ、次の節目まで追いたい。今は議事録と TODO の整理を毎回頼んでいる。

受入の条件
- メインが判断を決の項目にし、関係するタスクと具体例（原文と日付）を付けて出す。どちらかが欠けた項目は「つながりなし」と出る

### S5 worker が止まったら気付き、その端末に飛ぶ（P4）
worker が止まったとき、どの案件のどの worker が何で止まったか（許可待ち・返事待ち・中断・エラー・落ちた・ログイン切れ・利用枠）を知り、すぐその端末を開きたい。今は気付くのが遅れる。

受入の条件
- 止まっている数が窓の上と列の行に、仕事の名前（worktree の表示名）と理由と止まってからの時間が操縦席の帯に出る
- 帯の印を押すと、その端末を Orca で前に出す。端末が無ければ、その worktree を Orca で開く

### S6 離席から戻ったときに、判断が要るところだけ見る（P2・P3）
離席から戻ったとき、留守中にエージェントが決めたことと、自分の判断待ちだけを見たい。今は artifact でまとめさせている。

受入の条件
- 窓の上と列で、どの案件から見るかが決まる
- 案件を開くと「あなたの番」が既定で、エージェントが決めたことはエージェントからの報告に理由と戻し方つきで並び、行ごとに「戻して」がある

### S7 判断するときに、1 枚で決めて返す（P1・P3）
判断するとき、背景・選択肢・具体例・原文がそろった 1 枚で決め、その場で返したい。今は会話の中で「B,D進めて」と返している。

受入の条件
- 最初に見えるのは パンくず（全体 › 大タスク › タスク。どれも押せる。S15）→ 何のため 1 行 → なぜ今決めるか → 決めるための情報（これは何か・今どうなっているか・入れるならどうするか・得られること・失うこと。開いた状態）→ 選択肢（名前と、同じ条件で比べた具体例 1 行）→ 返答のボタン（下に固定）。返答のボタンは高さ 500px の窓でも見える。決めるための情報のある判断では、選択肢は動かして見る
- 決めるための情報が欠けた判断は、一覧の行と詳細の頭に無い欄の名前が出る。「情報が足りない」を押すとメインに頼め、押した判断には「メインに頼み済み」が出る
- どの項目にも「別の答えで決める」の欄があり、選択肢に無い答えや「もう手で送った」を書いて送れる。質問（話したい）とは見出しで分かれる
- 背景（いきさつと原文）・選んだら起きること（比較の表か図）・選択肢の理由・この判断で変わること・関係するタスクは、既定では閉じた「詳細」の欄にある。詳細の欄が画面の外にあるときだけ、返答の列に「背景と比較を開く」のように中身の名前のボタンが出て、押すと開いてそこへ移る。図・比較・背景のどれも無い項目には出ない
- 外に送る文面（Slack・メール）は、選択肢の前に送る見た目に近い枠（宛先と、改行を保った本文）で読める。「本文をコピー」と「下書きを開く」がある
- 並びのある説明は箇条で描かれ、URL と PR の番号は押せる
- 図は詳細の欄の幅いっぱいに描かれ、字が小さく描かれる図は押すと拡大する
- 印は墨色の「決める」「聞く」「見て」。朱は期限が 24 時間以内か過ぎたものだけで、色・形（塗り）・文字（「! あと n 時間」）の 3 つで示す
- パネルと窓で同じ詳細・同じボタン・同じキー（j/k・1-9・Enter・e・z）。打鍵ひとつで決まらない（数字で選んで Enter）。選ぶ前のボタンは「選択肢を選ぶ」、選んだ後は「この案で決める」
- 決めたら残から消え、10 秒の間は「元に戻す」で戻せる。片付け済みで読み返せる
- メインには合図の 1 行だけを、取り消しの猶予が過ぎてメインが入力待ちのときに自動で送る。利用者に「知らせる」操作をさせない。メインが Orca のチャットで端末が無いときは、合図のボタンを出さず「次に話しかけたときに反映されます」と出る

### S8 顧客への返信を作るときに、聞かれていることとタスクの状態を並べる（P1）
顧客への返信を作るとき、聞かれていることと関係するタスクの状態を並べて見たい（推測）。今は Slack のスレッドを渡して整理させている。

受入の条件
- 聞の項目と関係するタスクが互いにリンクし、タスクの状態（色と形）が並んで見える

### S9 夕方に、片付いたものを確かめる（P4）
夕方や週の終わりに、何が片付いたかを確かめたい。今は「整理しておいて」と頼んでいる。

受入の条件
- 「対応済み」に要対応と同じ大タスクごとのまとまりで新しい順に並び、行に対応した日時、詳細に採った選択肢と誰が片付けたかが読める

### S10 メモリが苦しいときに、動いている数を見る（P5）
マシンが重いとき、いま同時に動いているエージェントの数を見て、減らす判断をしたい。今はマシンが落ちてから気付く。

受入の条件
- 窓の上に、プロセスが生きているエージェントの総数を小さく出す。メモリの数字は出さない

### S11 成果物を探すときに、すぐ飛ぶ（P1）
資料・議事録の場所にすぐ飛びたい。今は「どこにある？」と聞いている。

受入の条件
- 出どころ・成果物・資料のリンクに種類の印（Drive・PR・ページ・ファイル）が付き、押すと開く。ファイルは Orca で（日本語の名前・`path:行`・本線の子の worktree の中のファイルも）、URL は既定のブラウザで

### S12 窓を置きっぱなしにしても、邪魔にならない（P2・P5）
窓を左のディスプレイの上半分に置きっぱなしにしても、マシンを重くせず、Orca の使い心地を崩したくない。

受入の条件
- 常駐のプロセスは 1 つで、子プロセスを常駐させない。常時のメモリは 50MB を目安にする（測った値は README）
- 横長の狭い窓と広い窓の両方で崩れない。低い窓では決定のボタンが詳細の下に留まる
- Orca の前面を勝手に切り替えない。切り替えるのは「Orca で開く」・帯の印・出どころを押したときだけ

### S13 頼んだものができたら、その画面で見て返す（P1・P3）
利用者からの依頼（「フロー図を整理して」など）に対応する成果物ができたら、操縦席で見て「これでよい」か「直してほしい」を返したい。今は会話の中でリンクを探して見ている。

受入の条件
- 依頼は原文のまま帳簿に残り、全体のタブの上に「まだ済んでいない依頼」として古い順に並ぶ（先週以前でも済むまで残る）。依頼を開くと、タスクと worker の状態・成果物とその確認の状態が見える
- 承認の要る成果物だけが「見て」に出る。中身は 依頼の原文 → 見てほしい点 1〜3 → 開くボタン（PR があれば差分も）→ 「これでよい」「直してほしい」。承認の要らない完成の報告はリンク付きの報告に入る
- 「直してほしい」は、依頼と成果物の ID を入れた書き出しの入った入力欄を開き、書いて送るとメインに渡る
- 全部の見てが承認されると依頼は「承認済み・反映待ち」、メインが反映すると片付け済みに移る

### S14 項目について、その場で聞いて答えを得る（P1・P3）
判断や成果物を見ていて気になったことを、その項目の場で聞いて、その下に答えが積まれてほしい。今はメインのチャットに書いて、どの項目の話かを説明し直している。

受入の条件
- 「話したい」を押すと、その項目（決める・聞く・見て・タスク）の中に入力欄が開き、送るとやり取りが吹き出しで積まれる（あなた・アシスタント・メインと時刻）
- すぐの回答は読むだけのアシスタントが出し、その印が付く。判断の変更・作業・ファイルの変更が要る話なら、そう答えて「メインに渡す」が出る。回答できないときはそう出て、メインが次に読む
- 書きかけの文は、画面の描き直しで消えない

### S15 全体 → 大タスク → 確認の順に把握し、決められない確認は大タスクに上がって決める（P1・P2）
ふだんは、案件の全体（大タスクがいくつあり、どれが止まっているか）をつかみ、大タスクごとに何の案件で今どこまで進んだかをつかみ、そのうえで確認と判断をしたい。決めるときは確認の一覧から押してさっと決め、決められなければ、その確認が何の大タスク（管理表のどの行・誰の指摘）のためかに上がって読んでから決めたい。今は確認と大タスクがつながって見えず、何に対応するかを遡れない（2026-11-17「構造化されてないからどれが何に対応するとかよくわからん」「判断できないなら上のタスクを見て判断する」）。

受入の条件
- 全体タブの最上層に大タスクが手当ての要る順のまとまりで並び、各行に 状態の印・名前・今の様子と次の作業・工程の進み・要対応の件数と最短の期限が 1 行で出る。どの大タスクにも入らないタスクは「大タスクにつながらないタスク」の行に出る
- 大タスクの状態は、済んでいないタスクがあればその状態、タスクが全部完了でも開いた確認（依頼経由の成果物の確認も含む）があれば「あなたの確認待ち」、「全タスク完了かつ開いた確認なし」のときだけ完了。表の印・畳み・大タスクの画面が同じ判定を使う
- 大タスクの画面は、頭（題名・状態・工程の進み・今の様子と次の作業・ゴール）→ あなたの対応 → 経過（日付のある出来事を古い順に並べ、「今」と「次」で締める）→ タスク → 背景と資料（いきさつ・依頼の原文・出典）の順に、線と面で区切って出る。説明の無い大タスクには「ゴールといきさつが未記入」と出て、依頼の原文と出典はいつも出る
- 2 つ以上の大タスクに関係する確認は、要対応の一覧には代表の 1 か所だけに並び、関係するどの大タスクの画面の「あなたの番」にも出る。全体の行の件数は要対応の一覧でその大タスクに並ぶ確認だけを数え、行の合計は上の帯と左の列の件数と同じになる。大タスクの画面では、ほかの大タスクに並ぶ関係する確認を「ほかの大タスクと共通の要対応」として分けて出す
- 要対応の一覧は大タスクの見出しごとに並び、見出しの並びは中のいちばん近い期限の順。どの大タスクにも結び付かない確認は最後の「つながりなし」に入る。開いたときに選ばれるのは期限がいちばん近い確認
- 確認の詳細とタスクの詳細と大タスクの画面の上に、パンくず（全体 › 大タスク › タスク）が出て、どれも押せる。確認の詳細には、ほかに関係する大タスクも全部押せる形で出る
- 上から下（全体の行 → 大タスク → 確認の行）と、下から上（確認のパンくず・一覧の見出し → 大タスク → パンくずの「全体」）が、それぞれ 1 クリックで移れる
- 確認から大タスクへ上がったときは、大タスクの画面とそこから開いたタスクの詳細に「確認『○○』に戻る」が出る。押すと、その確認が一覧と詳細の読んでいた位置のまま開き、選んでいた選択肢・書きかけの文・欄の開閉も残っている
- 大タスクの状態と、確認がどの大タスクに関係するかは画面が決める（`src/state.ts`）。メインが書くのは大タスクの説明（`streams[].summary`・`background`・`sources`）だけで、要対応のある大タスクには必ず書き、それ以外は任意。古い形の cockpit.json もそのまま表示できる

## 画面の要素と原則
| 要素 | 原則 | ストーリー |
|---|---|---|
| 窓の上: あなたの番の件数と内訳（決める・聞く・見て）・止まっている worker の数・いちばん急ぐ 1 件 | P2・P4 | S1・S6 |
| 窓の上: Orca で表示中／固定中・Orca に合わせる・Orca で開く | P2 | S2 |
| 窓の上: エージェントの総数 | P5 | S10 |

| 帯: 止まっている worker（仕事の名前・理由・端末を開く）・プラグインが止まっている理由 | P1・P4 | S2・S5 |
| 要対応: 大タスクごとのまとまりの判断・確認・質問と、その後に並ぶエージェントからの報告 | P1・P3 | S4・S6・S7・S13 |
| 詳細: たどりと何のため・送る文面・選択肢と具体例・資料のリンク・閉じた詳細の欄（背景・比較・理由・変わること・タスク）・返答・出どころ | P1・P3 | S7・S11 |
| 見て: 依頼の原文・見てほしい点・開くボタン・これでよい・直してほしい | P1・P3 | S13 |
| 話したいこと（項目ごとのやり取り・メインに渡す） | P1・P3 | S14 |
| つながりなしの印 | P1 | S4 |
| 報告の「戻して」 | P3 | S6 |
| 全体: 手当ての要る順の大タスクの行（今の様子と次の作業・工程の進み・要対応の件数と期限）と、横の列の節目・顧客への確認・まだ済んでいない依頼 | P1・P4 | S3・S13・S15 |
| 大タスク: 頭（状態・工程・今の様子・ゴール）・あなたの対応・経過（今と次）・タスク・背景と資料 | P1 | S15 |

結び付かない要素は今は無い。帯の「更新 n 分前」はメインの書き忘れに気付くためのもので P4 に入れた。キーの一覧は慣れれば要らないので、常には出さず「?」で出す。

## 採らなかったもの
- 窓に別の情報（PR・CI・カレンダー）を足すこと: 正は GitHub や各ツールにあり、同じ管理を重ねない（P2）
- 窓の位置を固定する仕組み: 一度置けば macOS が覚える
- メモリの数字の表示: 判断を変えるのはエージェントの数で、細かい数字は負荷になる（P2）
- 「今週の流れ」の帯と、worker の常時の入れ子の表示: 読む入口が増える。worker の状態はタスクと依頼を開いたときに出す（P2）
- すべての成果物を「見て」にすること: 判断が依頼の数だけ増える。承認の要るものだけにする（P2・P3）
