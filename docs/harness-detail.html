agent-harnessの詳しい図（全体像・タスクの分類・処理の流れ）

1背景と前提

agent-harnessは、Orcaで複数のエージェントを並べて動かすときに、深田さんが判断と大事な確認にだけ頭を使えるようにする道具の集まりです。13:05に入れた見取り図は、役と知らせの経路の概観に絞り、カードの種類・hook・ファイルごとの読み書きはREADMEとskillを指すだけにしていました（見取り図のQ3）。

11/23 14:12の依頼「このハーネスの全体像とかタスクの分類とか処理フローとかを詳細まで図にして」を受けて、このページでは見取り図より細かく、誰がどのファイルを読み書きするか、タスクがどう分類されて状態がどう決まるか、発言から済までの流れを図にしました。欄の定義はすべてcockpit skillの references/schema.md にあるので、このページでは図と流れだけを扱い、各節の「細部」から元の文書を指します。

IDの先頭の文字は次のとおりです。章と節は数字、図は図1〜図14、結論はK、用語はV、ファイルはF、タスクの判定はJ、流れはA（発言から済）・B（窓の操作）・C（窓からの質問）・M（圧縮と再開）・S（席と帯）、書く道具の規則はW、確かめてほしいことはQ。

ID語何か
V1窓操縦席の窓。左のディスプレイのブラウザタブ（127.0.0.1:47231）で、要対応・全体・対応済みの3タブ。Orcaの右サイドバーのパネルも同じ部品で出る

V9帳簿各ワークスペースの .orca/cockpit.json と、その周りの記録（操作・判断・発言・知らせ）

2結論

  • K1どのファイルも書き手は1種類です。帳簿は窓口だけが cockpit-write で、操作の記録は窓だけ、発言と知らせの記録はhookだけ、窓の上の帯はstallwatchだけが書きます（図1・図2）。
  • K2タスクの状態は誰も手で書きません。手で書くのは「済んでいない（open）」と「完了（ok）」だけで、残りは state.ts の judgeTasks が10の判定を上から順に照らして、事実から決めます（図8）。
  • K3どの流れも「記録に残す → 1行の知らせで起こす → 窓口が記録を読んで帳簿に書く」という同じ形です。知らせが失われても、hookが記録から名指しして拾い直します（図9〜図12）。
  • K4cockpit-write が断る規則は24の束で、受付・タスクの書き込み・操作の反映・文面・返しの反映の5か所で書き込みを止めます。通らなければ何も書かずに理由を返します（図14）。

3全体像

3.1登場するもの

深田さんが触るのは「画面と会話」の層だけで、その下のOrca・道具・記録は、エージェントと道具のあいだで閉じています。

細部
  • 担当とworkerを立てるのは窓口か担当で、知らせはみなOrcaのorchestrationを通る（見取り図の3.1・3.2）
  • Botは1つの案件を受け持ち、その案件の窓口のRunにだけ送る（cockpit skillのSKILL.md「仕事の形」、R144）
  • hookは compaction-keep.py（発言・知らせの記録、圧縮と再開）と periodic-reminder.sh（state.tsの checks を【操縦席】の行で流す）が主で、どちらもモデルを呼ばない

3.2誰がどのファイルを読み書きするか

どの行も書き手は1つで、担当とworkerは帳簿と記録を読み書きしません。決まったことは窓口に知らせで届き、窓口が書きます。

細部
  • F1は cockpit-write だけで書く。Write・Editで書こうとするとhook（compaction-keep.py のPreToolUse）が断り、書く道具を案内する
  • F3は窓口が compaction-keep.py rule で1行ずつ足す。撤回も置き換えの行で書き、消さない
  • F8の控え（ask-<質問id>.md）の冒頭は窓が立てる consult --ask が書き、質問と答えはhookが足す。返し（.returns.jsonl）はhookだけが書き、窓口とstate.tsは返しをここからだけ読む
  • F9は compactions.jsonl・keep.json・handoff.json・main-session.json。窓は引き継いだことを1日間出すために handoff.json を読む
  • F10は見張りの3つのプロセスのうちstallwatchだけが書き、ほかの2つは自分のファイルに書いてstallwatchに合流させる（5.5）
  • 元の文書: cockpit skillの references/schema.md「ファイル」

4タスクの分類

4.1仕事の3つの形

仕事の形によって深田さんの関わり方が決まり、その形は仕事のタスクに引き継がれます（R51）。

細部
  • 共同作業中の行は、担当のチャットの様子からstate.tsが作る。担当がまだ問いを送っていない仕事も出るので、窓口はこの行のためにカードを書かない（R145）
  • 見張る仕事の watch には、Orcaのautomationのid・対象・送り先だけを書く。頻度・前回の結果はOrcaが持つので写さない（R152）
  • 形の無い仕事は checks.no_form で名指しされる
  • 元の文書: cockpit skillのSKILL.md「仕事の形」

4.25つの工程

工程は5つで固定し、タスクが終わったときに何ができているかで1つ選びます。

細部
  • 5つの工程に無い名前は checks.unknown_phase、仕事に入っていないタスクは checks.loose_tasks で名指しされる
  • 見張る仕事のタスクは工程を省いてよい
  • 元の文書: cockpit skillの references/schema.md の tasks[] の phase

4.3カードの8種類と、私の番に数える5種類

私の番に数えるのは停止・許可・判断・送信前・確認の5種類で、結んだタスクを済にするのは確認の「承認」だけです。

細部
  • 相談は要対応に並ぶが数えない。受信は全体のタブの「見張る」、報告は要対応の下の「報告（参照のみ）」に並ぶ
  • 判断・許可・確認・送信前の「直しを伝える」は、カードを閉じずに本文つきの操作として担当に届く。そのあいだタスクは「修正中」で、件数から外れる（図8のJ6）
  • Orcaで止まったworkerや担当は、窓口が書かなくても窓が停止の票にする。窓口が停止のカードを書くのは、担当が質問で止まったときだけ
  • 出す範囲は、外に出るもの・戻せないもの・要件や設計が変わるものの3種に絞る（R52）。元の文書: cockpit skillの references/cards.md「何を私の番に出すか」と references/schema.md「カード」

4.4依頼・仕事・タスク・カードの結び

依頼は元の発言を指し、タスクは依頼とカードから指されて自分の仕事を指します。どの結びも帳簿のidで書きます。

細部
  • 依頼は1つの発言から2件起こしてよく、それぞれに引用の範囲を書く。発言の記録で結べない依頼は source に出典を書く
  • タスクの worker には、立てたときの最初のTaskのidを書き、あとから書き換えない。続きを頼むとOrcaはTaskとDispatchを新しく作るが、state.tsが続き（follow_up_of）をたどって今のDispatchを引く
  • カードの中身（選択肢・対象・本文・期限）を変えたら rev を1上げる。操作は押したときの item_rev を持ち、古いrevへの操作は反映されない
  • 元の文書: cockpit skillの references/schema.md「cockpit.json の形」「依頼の帳簿」

4.5依頼と仕事の状態

依頼と仕事の状態は帳簿に書かず、証拠・タスク・カードからstate.tsが決めます。

細部
  • 依頼の済は、済の条件（done_when）の1つ1つに証拠が1つ以上あるとき。質問（kind: question）は結論と根拠を書いた回答（answer）の証拠も要る（R47）。タスクが0件でも、空のまま済にはならない
  • 確認が要る依頼（check: true）は、今のカードの rev に押された取り消されていない「承認」が証拠にあるときだけ済。成果物を改訂して rev を上げると、古い承認は証拠にならない
  • 仕事の状況の文（status）は窓口が書くが、元の事実が変わると cockpit-write が書き直しを求める（6章のW18）
  • 元の文書: state.ts の requestViews・jobViews、cockpit skillの references/schema.md「依頼の帳簿」「仕事の行の語」

4.6タスクの状態の決まり方

窓口がタスクに手で書くのはopenとokだけで、それ以外は上の10の判定の順で、事実から決まります（R204）。窓・パネル・hook・書く道具がみな同じこの関数を通します。

細部
  • J3が4・5より上にあるのは、workerが動いていても終わっていても、次に動くのが深田さんだから。worker_doneの取り込み待ちより深田さん待ちが勝つ
  • J5のworkerの様子は、Orcaの今のDispatch（orca orchestration worker-show）から窓とhookが引く。書く道具とパネルはOrcaの様子を入れずに判定する
  • 担当はworkerに数えない。担当の受け取りは owners[].worker に書き、タスクの worker に古い担当の受け取りが残っていても（Dispatchのチャットが同じ仕事の開いた担当のもの）、J4・J5に当てない。開いた担当のいる仕事の着手できるタスクは、J10で「担当「<題>」が受け持つ」と出る（t159）
  • 待ちは4種類だけ書ける。深田さんを待つものは wait に書かず、頼むカードの tasks から指す。person・eventの待ちを解いた事実は、発言・知らせ・操作・議事録を wait.met[] の by で指して書く
  • カードの効果は図5の右の列。J1の「承認」は、窓口がまだ反映していない今のrevへの取り消されていない承認か、窓口が深田さんの操作で閉じたカードの今のrevへの承認
  • 元の文書: cockpit skillの references/schema.md「タスクの今の決まり方」（ここと同じ10の判定で書いてある）

5処理の流れ

5.1発言から済まで

発言は届いた時点でhookが記録し、窓口が依頼にしてから、済の条件ごとの証拠がそろうまで済になりません。

ID何が起きるか抜けたときに拾うもの
A1深田さんが窓口のチャットで発言するなし
A2hook（compaction-keep.py のUserPromptSubmit）が発言の原文に u-<行番号> を付けて utterances.jsonl に足す。Orcaの知らせは notices.jsonl に n-<行番号> で残すモデルを通さないので落ちない
A3hook（periodic-reminder.sh）がstate.tsの checks.unsorted を【操縦席】の行で流す。窓口はそのターンのうちに、新しい依頼・既存の依頼への追記・依頼でない、のどれかに仕分ける仕分けずに終えようとするとStopのhookが1回止める
A4窓口が依頼（done_when・kind・check）とタスクを書き、intake.through を進めるまたいだ発言があれば cockpit-write が断る（W6）
A5窓口が orca-launch --cockpit-task でworkerを立てる。briefの先頭にworkerの決まり、末尾に依頼の済の条件が自動で付く。受け取ったRunとTaskのidをタスクの worker に書く線を越えて動いていないタスクは checks.idle_tasks
A6workerが worker_done（確かめたコマンドと出力・commitのSHA）を送り、Orcaが窓口を起こす取り込み待ちが10分を超えるとhookが名指しする（checks.intake）
A7窓口が、workerの「仮定」からではなく済の条件を起点に証拠を照らし、git merge --ff-only でmainに入れる。条件を変えて済ませたものは判断のカードに回すなし
A8窓口が依頼の evidence にcommitを結び、タスクをokにする。深田さんの確認が要るものは、openのまま確認のカードで指す証拠の無い済の条件は checks.unproven、取り込んだのにopenのタスクは checks.stale_tasks
A9深田さんが確認のカードで「承認」を押す（5.2の流れ）。窓口はそのopを依頼の evidence に結ぶ未反映の操作として名指し（checks.pending_ops）
A10state.tsが、済の条件ごとに証拠がそろい、確認が要るものは今のrevへの承認もあるときに、依頼を済と出すなし
細部
  • 窓口が自分で引き受けた仕事（「直します」と返したもの）も依頼として受け、source に窓口の返事の原文を書く
  • 担当を立てる仕事では、窓口が先に仕事の形を決め、orca-launch --lead で担当を立てて担当の行（owners[]。受け取りの worker を持つ）を書く。担当がさらに自分のworkerを立てる。一緒に作る仕事では窓口はworkerを立てない（orca-launch が断る。t159）。担当から窓口へは worker_done と「判断: <題>」の2つが届く
  • 都合での先送り（「別PRで」「落ち着いてから」）は、Stopのhookと worker_done の送信前のhook（defer-guard.py）が1回差し戻す（R193）
  • 元の文書: cockpit skillの references/intake.md、worktree-flow skillの SKILL.md「窓口・担当・worker」

5.2窓の操作が帳簿に入るまで

窓は押した操作を記録に足して1行の知らせで窓口を起こし、窓口が記録を読んで、カードの変更と反映した操作の番号を1回で書きます。

ID何が起きるか抜けたときに拾うもの
B1深田さんが窓かパネルでボタンを押す（例: 確認の「承認」）なし
B2窓が cockpit.user.json に操作を足す（op_id・item_id・item_rev・type）。古いrevのカードへの操作は画面が断るなし
B3押してから10秒は「この操作を元に戻す」で取り消せる。取り消した組は窓口に送らないなし
B4窓が郵便受けの端末を送り主にして、窓口のRunへ「【操縦席】未反映の操作があります」を orca orchestration send で送る（R191）。どこまで送ったかは窓が notified.json に持つ帳簿に main.run_id が無いと送れず、窓の上の帯に理由が出る
B5窓口が applied_ops に無い操作を集め、取り消しの組を外し、今の rev と違うrevへの操作は適用しない届かなくても、hookが発言のたびに未反映の件数を出す（checks.pending_ops）
B6窓口が操作の種類ごとに反映し、カード・タスク・依頼の変更と applied_ops を cockpit-write の1回で書く2回に分けると、間に読んだ画面とhookが同じ操作を未反映と数える
B7窓とパネルが帳簿を読み直し、state.tsの判定で描き直すなし
細部
  • 操作の種類（type）: 決定 decide・承認と許可 accept・送信済み sent・却下 skip・一任 delegate・協議と直し talk・既読 ack・戻させる revert・取り消し undo・記録の再読 repeat・停止の票を片付ける dismiss・質問の答えを返す ask_decide・停止の行に窓から答えた記録 answer・整理・棚卸しの指示 tidy（カードを持たず、結果は報告のカードの tidy_op で結ぶ）。種類ごとの反映はcockpit skillの references/ops.md
  • 「直しを伝える」は本文つきの talk。窓口は本文を担当に send --to dispatch: で送り、applied_ops に足すだけにする。カードの rev を上げると直す前に私の番に戻るので上げない。直したものができたら rev を上げ、私の番に戻る
  • dismiss と、質問の ask_decide はこの知らせを送らない（ask_decide は返しが届いてから5.3の流れで反映する）

5.3窓からの質問

写しの会話は読むだけで、決まったことは返しの記録を経て、窓口が判断の記録と帳簿に書き、担当とworkerに伝えたときにだけ作業に反映されます。

ID何が起きるか抜けたときに拾うもの
C1深田さんが窓の「質問」の欄（全体のタブの上・カードの詳細・タスクの詳細）に打つ。hookが発言の記録に ask 付きで残すほかの発言と同じく仕分けの対象（A3）
C2窓が consult --ask で、main-session.json の窓口の会話を写した相手を窓口のworktreeのタブに立てる。タブは前に出さない窓口がまだ発言していないと立たず、窓が「窓口の会話が分かりません」と出す
C3相手はRead・Grep・Globだけで答える。hookがStopで答えを控え ask-<質問id>.md に足すなし
C4窓が控えを読み、右の欄に答えを出すなし
C5深田さんが「この答えを窓口に返す」を押す。窓が ask_decide の操作を書く操作が残るので、相手が止まっても窓口が拾える
C6窓が相手のタブに「返しを書いて（op <番号>）」を送る（orca terminal send。相手は check を打てないので知らせの経路の例外）返しが無いあいだは checks.unreflected_returns が名指し
C7相手が答えの末尾に【窓口への返し】のJSON（決まったこと・新しい依頼・残る論点・影響するタスク）を書くなし
C8hookが返しを ask-<質問id>.returns.jsonl に保存し、窓口のRunに「質問 <id>: 返し <return_id>」を送る知らせが失われても、返しの記録から名指しされる
C9窓口が compaction-keep.py ask-context で、質問のあとに増えた判断と、有効な判断との食い違いを照らす。増えていれば保留、食い違えば判断のカードで深田さんに聞くなし
C10窓口が rule で判断の記録に書き（from_return 付き）、cockpit-write で asks[].from_returns・新しい依頼・操作の番号を書く記録か帳簿の片方だけなら checks.unreflected_returns
C11影響するタスクに作業中の担当かworkerがいれば、send --to dispatch: で決まったことを送り、返ってきたmessageのidを notify[].message_id に書くidの無い行は「担当への通知」として名指し
C12窓口が相手のタブに「反映済み <return_id>」を送るなし
細部
  • カードの相談（担当のいないカードの「窓口と協議」）も同じ形。違いは、相談がそのカード専用のタブで、返しがカードの rev と選んだ選択肢を持ち、窓口がカードの今の rev と照らす点と、反映の印がカードの from_returns である点
  • 相談と質問の返しは、どれも「判断の記録に書く → 帳簿の印を書く」の順で、帳簿の印が最後の書き込み（反映し終えた印）になる
  • 元の文書: cockpit skillの references/consult.md

5.4圧縮と再開の確かめ

圧縮のあとは記録から原文を流し直し、窓口が照合に通るまで、担当とworkerへの新しい指示をhookが止めます。

ID何が起きるか使うもの
M1圧縮の前に、決まった見出しの薄い要約を書かせる指示を出す。決定・制約・原文は会話の外の記録にあるので要約に写させないcompaction-keep.py のPreCompact
M2圧縮の直後に、要約を記録と照らし、撤回された判断のID・却下した案・落ちたパスを compactions.jsonl に残すPostCompact

5.5席の切り替えと見張りの帯

見張りのプロセスはそれぞれ自分のファイルに書き、窓の上の帯へはstallwatchだけがまとめて書きます。窓口の会話へは、窓口の判断が要るときだけ送ります。

ID何が起きるか使うもの
